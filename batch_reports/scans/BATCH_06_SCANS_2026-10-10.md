### The one genuine finding — B314, XML entity-expansion exposure

Locations:

- `products/P060/src/traceaudit/testreports.py:211` — product code
- `products/P060/validation/validate_self_trace.py:64` — validation script
- `products/P058/validation/validate_tests.py:59` — validation script

The two validation scripts parse XML that the same script has just generated, so
the input is not attacker-controlled and the exposure is nil.

**`products/P060/src/traceaudit/testreports.py:211` is different, and it is the
only place in the batch where a product's core function is to parse XML supplied
from outside it.** TraceAudit reads a junit XML file named by the user. Python's
`xml.etree.ElementTree` does not retrieve external entities or remote DTDs, so
XXE and SSRF do not apply, but it **is** vulnerable to entity-expansion
denial-of-service — the "billion laughs" and quadratic-blowup classes — because
internal entity declarations are expanded. A hostile junit XML file can therefore
exhaust memory in the process reading it.

**Severity assessment, stated as a judgment and not as a measurement:** low for
the documented use, which is reading the junit XML your own test run just wrote.
It is not low for anyone who points the tool at a report arriving from outside
their trust boundary, for instance a vendor's or a subcontractor's build output —
which in an aerospace assurance context is not a far-fetched use.

**Action taken:** the exposure and its mitigation (`defusedxml`) are now
documented in P060's README limitations and in its VALIDATION.md. The dependency
was **not** added, because P060 ships with zero runtime dependencies by design
and that property is itself documented and tested; trading it away unilaterally
on an unattended night is not this session's call. **Recorded as an open,
documented, non-critical finding, not as resolved.**
