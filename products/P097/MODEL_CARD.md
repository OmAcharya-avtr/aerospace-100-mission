# Model card — flakerank intermittency-cost predictor

Validation level: **Level 2.** The model is trained and scored entirely on a
committed synthetic run history generated by `data/generate_history.py`. It has
been exercised against no real CI system, and every figure below is a property
of that generator as much as of the model. Nothing here is a measurement of a
production test suite.

**This model is not certified for operational flight use.**

> Every metric in this card was produced by `validation/validate_learned_model.py`
> in this session, over `data/run_history.json` (sha256
> `aa12f8cc861ba66008a0d3762cd68fa24a24b013f897da67c8151996c531b18a`). The raw
> transcript is `validation/validate_learned_model_output.txt`. Every number can
> be regenerated with `python3 validation/validate_learned_model.py`.

## Problem

Over the next `H` CI sessions, which tests will waste the most machine time?

Not "is this test flaky". A flaky-test dashboard already answers that, and the
whole argument of this product is that the answer is not the useful one: the
cost of a flake is its failure rate multiplied by its runtime, and a rate alone
cannot order two tests by cost.

Rows are `(origin session, test)` pairs. Features are measured over the lookback
window `[o - L, o)`; the target is the wasted seconds the test actually accrued
in the horizon window `[o, o + H)`. No feature can see its own target, and
`tests/test_predictor.py::test_features_cannot_see_their_own_target` checks that
structurally rather than by inspection.

| setting | value |
|---|---|
| lookback `L` | 120 sessions |
| horizon `H` | 30 sessions |
| training origins | 120, 150, 180, 210 |
| held-out TIME origins | 240, 270 |
| minimum attempts per row | 8 |
| rows built | 432 |
| training rows | 200, over 50 tests |
| held-out TESTS rows | 88, over 22 tests |
| held-out TIME rows | 100, over the 50 training tests |

## Baselines, implemented and validated first

All three were implemented and checked **before** the learned component was
written, and validated against the generator's own expectation in
`validation/validate_baselines.py`. The mission's build guide requires that
order, because an under-strength baseline inflates an apparent learned win and
an earlier product of this mission published a margin about 50 per cent too
large for exactly that reason.

1. **Flake rate** — `failed_attempts / attempts` over the lookback window. The
   thing being refuted, implemented at full strength: a pooled maximum-
   likelihood estimate over every recorded attempt including retries. It has no
   seconds interpretation, so its error metrics are reported as `n/a` rather
   than as a number that would invite a comparison the units do not support.
2. **Analytic expected cost** — `S * t_fail * E[F_m(p)]` with the geometric
   expected failed-attempt count in closed form, scaled to the horizon.
   `src/flakerank/geometric.py` derives it and states where it stops being
   valid.
3. **Accumulated persistence** — the lookback window's accumulated wasted time
   scaled to the horizon. This is baseline 3's accumulation used predictively.

An **oracle** that knows the realised target is scored alongside, to show the
ceiling each metric can reach.

Against the generator's own expected wasted time, over the whole committed
history (`validation/validate_baselines_output.txt`):

| ranking | Kendall tau-b | Spearman rho |
|---|---|---|
| baseline 1, flake rate | 0.729281462 | 0.860134282 |
| baseline 2, analytic expected cost | **0.896547852** | **0.920010948** |
| baseline 3, accumulated wasted time | 0.895432743 | 0.919895282 |

## Architecture

`sklearn.ensemble.RandomForestRegressor` on `log1p(wasted seconds)`.

| hyperparameter | value |
|---|---|
| `n_estimators` | 300 |
| `max_depth` | 5 |
| `min_samples_leaf` | 5 |
| `random_state` | 97044 |
| `n_jobs` | 1 |

A forest rather than anything larger, for three hard constraints and not
preferences: the training set is 200 rows from one history, so a model with many
parameters memorises rows; the build environment has two cores shared by five
concurrent agents and a 60-second budget for any fit; and a forest gives a
spread across trees that is an honest, if conservative, uncertainty output
without a second model. `n_jobs=1` is deliberate — parallel tree fitting on a
contended two-core box is slower than serial — and this product measures no fit
time at all, because asserting on one would be the wall-clock defect class it
exists to refute.

The target is `log1p` because the raw target spans five orders of magnitude and
a squared-error fit on the raw scale would be determined by the two slowest
tests.

### Features

17 columns, all computable from the lookback window alone:
`sessions`, `attempts`, `attempts_per_session`, `failed_attempts`,
`log1p_failed_attempts`, `failure_probability`, `session_failure_fraction`,
`mean_attempt_seconds`, `log_mean_attempt_seconds`, `sd_attempt_seconds`,
`max_attempt_seconds`, `min_attempt_seconds`, `mean_failing_seconds_or_mean`,
`wasted_seconds`, `log1p_wasted_seconds`, `analytic_cost_per_session`,
`late_failure_fraction`.

The model is **given the baselines' own outputs** as features
(`analytic_cost_per_session`, `wasted_seconds`). That is the fair comparison: a
learned model that lost because it was denied information the baselines had
would prove nothing.

Impurity-based importances of the fitted forest, largest first. These describe
the forest; they are biased towards high-cardinality features and are not a
causal claim.

| feature | importance |
|---|---|
| `analytic_cost_per_session` | 0.3399693389703807 |
| `wasted_seconds` | 0.32644603859189514 |
| `log1p_wasted_seconds` | 0.2818601186220956 |
| `attempts` | 0.01609153276368615 |
| `sessions` | 0.00879203593537771 |

The three largest are the two baselines' outputs and a monotone transform of
one of them. That is itself part of the finding.

## Test-split strategy

Two generalisation questions, scored separately because one number cannot
answer both. One fit, two evaluations; neither evaluation feeds back.

- **Held-out TESTS** — 22 tests withheld entirely, scored at the training
  origins. Does the model transfer to a test it has never seen?
- **Held-out TIME** — the training tests, scored at origins 240 and 270, after
  the committed history's declared regime change at session 230, where ten of
  the seventy-two tests change their failure probability. Does what it learned
  still hold later?

`tests/test_predictor.py` asserts that the two splits share neither a test nor
an origin, so they are genuinely different questions and not one split under two
names.

**Zero inflation, reported because it dominates every rank metric.** Over a
30-session horizon most tests waste nothing: 25 of 88 held-out-TESTS rows and 34
of 100 held-out-TIME rows have a non-zero target. A score that separates zero
from non-zero therefore does well on Spearman without saying anything about how
much.

## The finding

**A classical baseline matches or beats the learned forest.** Counted over the
two splits and the four metrics a baseline and the model can both be scored on,
with an exact draw counted as a shared cell rather than a win for whichever name
was checked first:

| predictor | share of 8 cells | outright wins |
|---|---|---|
| analytic expected cost | 2.83 | 2 |
| flake rate | 2.00 | 2 |
| accumulated persistence | 1.83 | 1 |
| learned forest | 1.33 | 1 |

The specification for this product predicted that the analytic cost model would
be strong and might well win. It does. The forest's three largest feature
importances are the analytic cost, the accumulated wasted time and a transform
of the latter — that is, the baselines' own outputs. A forest whose signal is a
closed form it was handed is not adding a model; it is adding variance to one.

**This result is published as the finding. It was not retuned away**, the model
was not denied features the baselines had in order to lose, and the model was
not re-fitted after seeing the scores.

Two honest qualifications, in both directions:

- The flake rate wins on **Spearman** on both splits. That is a real result and
  it is reported. It happens because the target is zero-inflated and the rate
  separates zero from non-zero well; it says nothing about magnitude, which is
  why the same predictor captures only 0.269 of the realised waste on held-out
  TESTS against 0.962 for the analytic model. Spearman and capture are both
  reported for that reason.
- The forest holds the single largest capture figure on held-out TESTS
  (0.979481 against 0.961962). That is one cell of eight, the margin is 0.0175,
  and it is not a basis for preferring the forest.

## Uncertainty output

`predict()` returns a `PredictionWithConfidence` carrying, per row, the ensemble
mean, the standard deviation across the 300 trees, and a central interval from
the tree quantiles at a nominal 90 per cent. All three are in `log1p` seconds.

Measured coverage of the realised target by the nominal 90 per cent interval:

| split | nominal | measured | mean interval width (log1p s) |
|---|---|---|---|
| held-out TESTS | 0.90 | 0.909091 | 0.9608410060412717 |
| held-out TIME | 0.90 | 0.830000 | 0.8442475051938403 |

**What that spread is and is not.** It is the disagreement among trees, which is
an epistemic quantity: large where the training rows were sparse, small where
they were dense. It is **not** a predictive interval for a new observation,
because it excludes the irreducible session-to-session variation of a Bernoulli
failure process, which for a rare flake dominates everything else. The measured
0.83 on held-out TIME, below the nominal 0.90, is consistent with that and is
reported whatever it is.

## Failure cases

1. **The interval can collapse to `[0, 0]` while the point prediction is
   positive.** For a test that almost never fails, nearly every tree predicts
   `log1p(0) = 0` and a handful predict a positive value, so the distribution
   across trees is a point mass with a thin right tail and its central quantile
   interval does not contain its own mean. Measured: the mean lies outside the
   interval on 47 of 88 held-out-TESTS rows and 55 of 100 held-out-TIME rows,
   and the widest such interval anywhere is 0.00075841280849251 — that is, every
   escape happens where the interval is near-degenerate. Pinned in
   `tests/test_regressions.py`.
2. **A regime change is not anticipated.** The held-out TIME split sits after a
   change in which ten tests' failure probability moves by a factor of 4 or 0.2.
   The model has `late_failure_fraction` as its only trend feature and the
   measured interval coverage drops from 0.909 to 0.830 across that boundary.
3. **A test with no observed failure in the lookback window** has a measured `p`
   of zero and an analytic cost of zero, and the model learns from rows like it
   that the answer is zero. For a slow test that has not failed yet, every
   predictor here including the oracle-free baselines returns zero, and the
   honest statement is an upper bound on the rate that this product does not
   compute.
4. **Nothing here is calibrated to a real CI system.** The generator makes
   attempts independent, which real retries are not.

## Reproducibility

```bash
cd products/P097
python3 data/generate_history.py          # regenerates data/run_history.json
python3 validation/validate_baselines.py  # the baselines, validated first
python3 validation/validate_learned_model.py
python3 examples/model_against_baselines.py
```

Every stochastic step uses `numpy.random.default_rng` at seed **97044**, which
is the one seed declared in `data/generate_history.py`,
`validation/_bootstrap.py`, `examples/_bootstrap.py` and `tests/_support.py`;
`tests/test_determinism.py` asserts they agree. Two fits at the same
`random_state` predict identical values, asserted at zero tolerance in
`tests/test_predictor.py::test_fit_is_deterministic_at_a_fixed_random_state`.

**No model is serialised.** Nothing in this repository writes a `.joblib`,
`.pkl` or `.ckpt` file, and `validation/validate_tree_hygiene.py` checks the
tree for one. A scikit-learn pickle is not portable across minor versions —
1.9.1 cannot unpickle a 1.8.0 model, measured in this mission — so the forest is
refitted from the committed history whenever it is needed. The
`scikit-learn>=1.9,<1.10` ceiling in `pyproject.toml` is declared anyway, so the
numbers above belong to the version that produced them.

## Compute used

Measured versions: Python 3.13.18, numpy 2.5.3, scipy 1.18.1, scikit-learn
1.9.1, on x86_64 Linux with 2 cores shared by five concurrent build agents.

The fit is 300 trees of depth 5 over 200 rows and 17 features. The whole of
`validation/validate_learned_model.py` — the row build, the fit and both
evaluations — completes well inside the mission's 60-second budget for a single
training run. **No duration is measured or asserted on anywhere in this
product**, so no timing figure is quoted here: that is the defect class this
product exists to refute, and quoting a wall-clock reading as evidence would
contradict it.

## Ethical and safety limits

- Research-grade. Not flight-qualified, not certified and not approved for
  operational aerospace use.
- **This model is not certified for operational flight use.**
- A ranking of tests by cost is a prioritisation aid, not a verdict on a test's
  correctness. A test ranked first here may be correct and the system under test
  may be the intermittent party; the product measures wasted machine seconds and
  has no opinion on cause.
- Using a cost ranking to decide which flaky tests to *delete* rather than fix
  would invert its purpose: the most expensive flake is often the one guarding
  the most expensive failure. The 1-in-44 intermittent failure that motivated
  this product was a real defect in a validation probe, not a nuisance.
- Every metric here is a property of a synthetic generator. Carrying a figure
  from this card into a claim about a real test suite is unsupported.
