# Model card — photoncount rate corrector 0.1.0

## Problem

Recover the **incident** photon-detection rate `n` from the **observed** count
rate `m` of a detector that has both dead time and afterpulsing. Each effect has
a textbook inversion that assumes the other is absent. They are not independent:
an afterpulse extends a paralyzable detector's dead period, and a dead period
suppresses an afterpulse, so the composition is not the product of the two
inverses. `validation/validate_simulator_output.txt` §7 measures that
non-commutation at up to **25.98 %** of the observed rate. There is no closed
form for the pair.

Output is a rate in counts per second with a 5th-to-95th-percentile interval.

## Baselines, implemented and measured first

| Baseline | Expression | Information it uses |
|---|---|---|
| Non-paralyzable inversion (D2) | `n = m / (1 - m τ)` | `m`, `τ` |
| Paralyzable lower-branch inversion (D5) | `n = -W₀(-m τ) / τ` | `m`, `τ` |
| Model-matched | (D5) if paralyzable else (D2) | `m`, `τ`, model |
| **Composed** | `n = invert_deadtime(m (1 - p))` | `m`, `τ`, model, `p` — **the same inputs the model gets** |

The composed baseline exists because the two textbook forms structurally cannot
accept an afterpulse probability, and beating a baseline denied an input proves
nothing. It is the baseline that matters.

## Architecture

Three `sklearn.ensemble.GradientBoostingRegressor` models with
`loss="quantile"` at α = 0.05, 0.5 and 0.95, predicting `log10(n τ)` from five
features. The α = 0.5 model is the point estimate, so point and interval come
from one family. Per-row outputs are sorted so the interval is always well
formed.

Hyperparameters: `n_estimators=250`, `max_depth=3`, `learning_rate=0.08`,
`random_state=0`. **No search was run.** They were chosen to fit the compute
budget and are reported as such, not as a tuned optimum. PyTorch is not available
in the build environment; this is a scikit-learn model by constraint as well as
by scale.

Working in `log10(n τ)` rather than in the rate is what lets one model cover five
decades of rate and two of dead time: everything about dead time depends only on
that product.

## Features

| # | Feature | Source | Units |
|---|---|---|---|
| 0 | `log10(m τ)` | measured observed rate × declared dead time | dimensionless |
| 1 | `fano_factor` | sample Var/mean of per-window counts | dimensionless |
| 2 | `afterpulse_probability` | declared | dimensionless |
| 3 | `log10(t_ap / τ)` | declared | dimensionless |
| 4 | `is_paralyzable` | declared | 0 or 1 |

Features 2 to 4 are datasheet values a real deployment would have. Feature 1 is
the only one carrying information a rate equation does not use — dead time
anti-bunches counts and pushes the Fano factor below 1, afterpulsing clusters
them and pushes it above 1. Measured below: at these counting statistics it
contributes nothing.

**A feature that was removed.** An earlier version exposed the mean count per
window. Because the generator sets the window length to `events_per_window / n`
to bound simulation cost, that feature equals `events_per_window × m/n` and
therefore contains the label. With it present the model hit the counting-noise
floor in every regime, including the regimes where the closed forms are exactly
right. It is gone, and
`tests/test_correction.py::test_dataset_has_no_mean_count_feature` keeps it out.

## Dataset

See `DATASET_CARD.md`. 6000 training rows (seed 20261006) and 2000 held-out rows
(seed 99001), generated by independent calls to
`photoncount.dataset.generate_dataset`, each row an event-level simulation of 25
counting windows. No row appears in both.

## Training procedure

```bash
cd validation
python3 validate_correction.py
```

Deterministic: the dataset seeds and `random_state=0` fix everything. Fitting
takes about 6 s; generating both datasets takes 20 to 30 s depending on container
load; the whole script runs in about 30 to 40 s on two shared cores. The timings
of the run that produced the numbers in this card are printed in
`validation/validate_correction_output.txt` §0, §2 and §8. The fitted model is written to
`validation/rate_corrector.joblib` (196 KiB, compressed joblib — no `.pt`,
`.pth`, `.ckpt` or `.onnx` is produced, and `RateCorrector.save` refuses those
suffixes).

## Metrics and test-split strategy

Held-out rows are generated from a separate seed, so the split is by
construction rather than by partitioning one draw. Metrics are relative error
in the rate, `(n̂ - n)/n`, reported as median absolute, 90th percentile, median
signed (bias), and mean absolute `log10` ratio, each over the rows the estimator
could answer, with the defined fraction reported alongside so an estimator that
answers only the easy half cannot look accurate by that alone.

**Counting-noise floor.** Median total counts per row is 4812, so the floor on
the observed rate is 1/√4812 = 0.01442 relative, and the smallest achievable
median absolute relative error is about 0.00972. No estimator can beat it.

Overall, held-out (`validation/validate_correction_output.txt` §3):

| Estimator | Defined | Median | p90 | Bias |
|---|---:|---:|---:|---:|
| non-paralyzable (D2) | 1.000 | 0.0418 | 0.1874 | +0.0237 |
| paralyzable lower (D5) | 0.863 | 0.0469 | 0.1692 | +0.0361 |
| matched | 0.989 | 0.0371 | 0.1307 | +0.0288 |

## Uncertainty output

The 5th-to-95th-percentile interval from the two outer quantile models. **Measured
coverage 0.8995 over 2000 held-out rows against a nominal 0.90** (binomial
standard error 0.0067, z = −0.07), with a median relative width of 0.2217.
Coverage is measured, not assumed, and is re-measured by
`validation/validate_correction.py` on every run.

The interval is a quantile estimate, not a calibrated confidence interval. It
inherits whatever the training distribution assumed; see failure cases.

## Failure cases

1. **Past the paralyzable maximum (`n τ > 1`) the model fails as badly as the
   closed forms** — median relative error 0.8399 against 0.8336 for the matched
   inversion. The forward map is two-valued there and nothing in the feature set
   resolves the branch. The preflight check in `photoncount.ops` **fails** a run
   planned at or above `1/τ` for this reason.
2. **It is beaten by the closed forms where afterpulsing is negligible**
   (`p <= 0.02`): 0.0243 against 0.0143. Use the closed form there.
3. **Outside the training ranges it is an extrapolation with no warning.** The
   model was fitted for `τ ∈ [20 ns, 1 µs]`, `n τ ∈ [0.002, 3]`, `p ∈ [0, 0.15]`
   and `t_ap/τ ∈ [0.3, 30]`. Nothing in the API checks the inputs against those
   ranges, and the interval does not widen outside them.
4. **It assumes the declared detector parameters are right.** Features 2 to 4 are
   datasheet values. A wrong declared afterpulse probability is a wrong input, and
   the model has no way to notice.
5. **It assumes the simulator is right.** The model is fitted on simulated truth.
   `validation/validate_simulator_output.txt` checks the simulator against every
   rate law it generalises, which is the strongest check available without
   hardware, and is not a substitute for a measured detector.
6. **It assumes a cascading afterpulse model with a single exponential release
   delay.** Real SPADs show multi-exponential or power-law tails.
7. **The Fano factor contributes nothing** at the counting statistics used.
   Flattening it to a constant leaves the model slightly *better*
   (0.0208 against 0.0234). Anyone expecting the Fano factor to separate the two
   effects needs far more counts per measurement than 5000.

## Reproducibility

```bash
python -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"
cd validation && python3 validate_correction.py
```

Seeds: training 20261006, held-out 99001, model `random_state=0`. Everything
else is derived. Re-running reproduces `validate_correction_output.txt` on the
same library versions; the generated rows depend on NumPy's `default_rng`
stream, so a different NumPy major version may shift the last digits.

## Compute used

Two shared cores of a cloud build container, no GPU, running concurrently with
four other build jobs. Dataset generation about 20 s, fitting about 6 s, whole validation
script about 30 s; the exact figures of the committed run are in its output file. Peak process RSS during the benchmark run was 197 MiB
(`benchmark/benchmark_results.md`). Inference: 0.75 ms for a single row, 16.4 ms
for 1000 rows batched, that is about 61000 rows per second — again on that
container, not on a Jetson.

## Ethical and safety limits

**This model is not certified for operational flight use.** It is research-grade
software for analysing a photon-counting receiver chain. It estimates a physical
rate from simulated detector behaviour; it makes no decision about a spacecraft,
a link or a person. It must not be used to correct a measured count rate in any
setting where the corrected number is relied upon without an independent check,
and it must not be used outside the parameter ranges in failure case 3.

No personal data is involved. The training data is synthetic and generated by
committed, deterministic code.
