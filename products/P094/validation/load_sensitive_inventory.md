# The load-sensitive assertion class in P094 — complete inventory

P094 measures timing. One half of every comparison it publishes is read from a
committed hardware campaign, and the other half is measured **live, in this
container, now**, by `hiltimingdiff.simulate.measure_simulation`. That container
has two CPU cores and is shared. So any check whose outcome depends on a live
wall-clock reading is, to some degree, an assertion about the machine's load
rather than about the product.

That is not a list of bugs. It is one class, and this file is the exhaustive
inventory of it. The design rule applied to every member:

1. a check on a live reading may assert a **DIRECTION** (`x > 0`, the sign of a
   quantity) or a **BOUND** against a value that is fixed — a pre-registered
   literal from SPEC §7, or a figure computed from the committed traces alone —
   with the measured band published in `validation/VALIDATION.md`;
2. **no check compares two separately-measured live wall-clock readings**, and
   no check asserts a ratio or an ordering between them;
3. where a timing relationship is needed for the claim to mean anything, the
   claim is moved onto the committed campaign, or onto a quantity that is
   deterministic in the seeds rather than in the clock.

## What depends on a live reading, and how

Everything in the live half flows from one function. The dependency chain is:

```
measure_simulation()            -> per-stage, per-cell, per-pass medians in ns   LIVE
  calibrate_ns_per_op()         -> one global scalar, ns per declared operation  LIVE
    baseline_1()                -> declared_ns, signed/absolute relative error   LIVE
    divergence(units, ns_per_op)-> R[s], ratio_interval                          LIVE
  baseline_2(units, simulation) -> per_stage_ratio, k, held-out error, splits    LIVE
  SimulationResult.elapsed_s    -> wall-clock duration of the measurement        LIVE
  SimulationResult.census       -> gate branch counts over seeded frames         NOT live
  SimulationResult.table.k_mean -> candidates per frame over seeded frames       NOT live
```

Two things measured by the same live run are **not** live quantities, and the
distinction carries most of this pass: `census` and `k_mean` are integer and
rational counts over frames generated by `staged_exec.make_frames` from the
campaign's own `synth_seed`. They are identical on every host under every load.
Measured 2026-11-19: a repeated call returned the identical census dictionary
and the identical per-cell `k_mean`, and a two-pass call returned exactly twice
each count.

Three published figures are **invariant** under `ns_per_op` and so do not depend
on the live half at all, even though a live scalar is passed in: the divergence
spread `max(R)/min(R)`, the Kendall tau-b, and the permutation. `ns_per_op` is a
single positive factor on every `R[s]`; it cancels in the spread and no rank
statistic can see it. That is why `validation/validate_drift.py` can take a live
measurement and still assert nothing load-sensitive.

committed or seed-deterministic data. Verdict `LOAD-SENSITIVE` means its outcome
can move with the machine's load; the right-hand column is what it was reduced

## The two amplifiers, stated plainly

`validate_approx_audit.py` runs the whole suite twice. `probe_working_directories.py`
runs every validation script four times. A single load-sensitive check therefore
gets six to ten extra draws per gate run, and when it fires inside one of those
two scripts the gate blames the amplifier rather than the owner. Neither is a
defect in the amplifier and neither is changed: they are listed so that the
reason for fixing this class at its design, rather than instance by instance, is
on the record.

## Out of class, but the same shape, and fixed

`validate_pypi_probe.py` asserted that the probe reached PyPI. Network
reachability is a property of this container, not of this product, so a run that
cannot reach PyPI used to exit 1 and block the gate for a reason no change to
the product could fix. It now records a FINDING, makes **no availability claim**
from that run, and exits 0. The name-availability claim itself is unchanged: it
is made only when the live TAKEN controls come back 200 in the same run.

## Diagnosability: why the 2026-11-16 message said "no output"

`scripts/release_gate.py` reports a failing script as
`<script> exit <code>: <last line of STDERR>`, and prints `no output` when
stderr is empty. Every line a validation script here writes — including
`[FAIL] <name>` and the `FAILED CHECKS (n)` footer — went to **stdout**, which
the gate discards. So `validate_measured_baselines.py exit 1: no output` was a
true statement about stderr that named neither the failing check nor the
measurement that failed it. The information existed and was thrown away.

`validation/_bootstrap.py` `Tee.save` now repeats the failing check names on
stderr, last, so the gate's one-line message names them. That change does not
make any check pass; it makes the next failure legible.

## A sixth defect, found while building this inventory

Not load-sensitive, and worse. `validate_tree_hygiene.py` deleted its own
previous output before scanning the tree — correct, because a scanner that
reports itself is not a check — but it deleted the hard-coded committed path
rather than the path the run actually writes. Those differ exactly when
`HILTIMINGDIFF_OUTPUT_DIR` redirects the output, which is what
`probe_working_directories.py` does to every script here. So a probe run
**destroyed a committed validation output** and wrote its replacement into the
temporary sink.

Found by a one-test discrepancy: the suite collected 1252 tests at the start of
a full pass and 1251 when the `pytest.approx` audit ran the same suite later in
the same pass, because `tests/test_honesty.py` parametrises over the tracked
text files in the tree. The gate hid it, running
`probe_working_directories.py` before `validate_tree_hygiene.py` in
alphabetical order so the file was recreated before anything looked.

Fixed by deleting `tee.path` and nothing else. Pinned as
`tests/test_regressions.py::test_regression_a_redirected_tree_hygiene_run_keeps_the_committed_output`.
Negative control measured to fire: against the pre-fix script the committed
output is gone after a redirected run; against the fixed script it is
byte-identical.
