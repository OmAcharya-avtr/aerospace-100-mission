# P092 DeadlineRisk — specification

**Class** flagship · **Category** autonomous-aerospace-systems ·
**AI** yes · **Validation level target** 4 (hardware) ·
**Package** `deadlinerisk` · **License** Apache-2.0

## The question

A hard-real-time autonomy loop has a period `T` and an implicit deadline
`D = T`. Practice sizes the margin from the mean and the standard deviation of
the measured execution time: *mean plus k sigma fits, therefore it is safe.*
That rule is a statement about the centre of a distribution being used to make
a statement about its tail, and the tail of an execution time on a shared
multicore SoC is not Gaussian — it is generated by preemption, cache and
memory-bandwidth interference from co-resident work.

**The headline output of this product is the factor by which the mean-plus-margin
rule understates the measured deadline-miss rate, with a confidence interval
that accounts for serial dependence between consecutive deadlines.** The product
is specified to report that factor whatever its value, including a value whose
interval contains 1, which would say the rule is adequate on this board under
this payload.

## What it does that existing tools do not

WCET analysers bound one task on an idle processor; real-time tracers (Ftrace,
LTTng, `cyclictest`) report observed maxima and latency histograms. Neither
turns an observed tail into a *miss probability with an interval* under named
co-resident contention, and neither states how far the mean-plus-margin rule it
is being used to justify is wrong. `cyclictest` measures scheduling latency of
an empty workload, not response time of a job with execution; extreme-value
libraries (`scipy.stats.genpareto`, `pyextremes`) fit a GPD but know nothing
about deadlines, dropped releases or serial dependence.

The alternatives table in the README names these and says when to use them
instead.

## Measurement model, stated once

- Job `i` is released at `t0 + i*T`; response time is `end - release`.
- A job whose response exceeds `D` is a **miss**.
- If a job finishes after later releases have already passed, those releases are
  never executed. They are **dropped**, and each dropped release is also a miss.
  Every executed row carries `dropped_before`, so
  `releases = sum(1 + dropped_before)` and
  `misses = sum(missed + dropped_before)` are both reconstructible from the
  committed traces.

This definition is the one every number in the product depends on and it is
stated in `README.md`, `VALIDATION.md` and the loader's docstring.

## Baselines — implement and validate in this order

1. **Baseline 1 — the mean-plus-margin rule. The thing being refuted.**
   `P(resp > D)` under a Gaussian with the sample mean and sample standard
   deviation of the measured response times. Implemented deliberately because it
   is what the practice does. Also expressed in the form practitioners use: the
   `k` for which `mean + k*sd = D`, so a reader can see which sigma level their
   own rule corresponds to.
2. **Baseline 2 — extreme value theory.** Generalised Pareto fit to
   peaks-over-threshold of the response times, `P(resp > D)` in closed form as
   `zeta * (1 + xi*(D-u)/beta)**(-1/xi)` with `zeta` the measured exceedance
   rate at threshold `u`. **A declared threshold-choice diagnostic is part of
   the deliverable, not an optional extra**: the shape and modified-scale
   parameters are reported over a range of `u`, and the chosen `u` is justified
   from that stability plot rather than asserted.
3. **Baseline 3 — ground truth.** The directly counted miss rate over the long
   measured run, with a **moving-block bootstrap** interval. An i.i.d.
   bootstrap is wrong here and the product says why: consecutive deadlines share
   contention state, so the effective sample size is smaller than the release
   count. The block length is chosen from the measured autocorrelation of the
   miss indicator and the choice is reported.

A fourth, classical predictor is required for the forecasting task and is not
fitted to anything: **speed-scaling** — with `m` cores and `n` busy co-resident
workers, the available fraction of a core is `min(1, m/(n+1))`, so predicted
response is the idle-run execution time divided by that fraction. This is the
textbook capacity argument and it uses only descriptors plus the idle-run
distribution.

## Learned component

A contention-aware predictor mapping **co-resident workload descriptors that an
operator could observe without running the task** — number of CPU and memory
stressors, measured foreign CPU occupancy, load average, mean and minimum core
clock, die temperature — to a miss probability, with an uncertainty output.

Dataset: the measured campaign split into fixed-length windows; each window
contributes its descriptors and its own counted miss rate. Scored **separately**
on:

- **held-out workload mixes** — grouped by run, so no window of a test mix is
  ever in training;
- **held-out time** — the later portion of every run held out, training on the
  earlier portion.

Expected result, recorded here before the data exists: the EVT fit is
competitive and any learned margin is smaller than the bootstrap half-width on
the counted reference. If so, that is the finding and it is published as the
finding. If the learned model wins by more than the half-width, that is also
published. Neither outcome is retuned away.

## Hardware campaign (this is a Level 4 product)

Measured on the **NVIDIA Jetson Orin Nano Engineering Reference Developer Kit
Super**, aarch64, JetPack R36.4.7, kernel 5.15.148-tegra, 6 cores, governor
`schedutil`, `cpuinfo_max_freq` 1728000 kHz, power mode `MAXN_SUPER`.

`scripts/p092_campaign.py` (committed) does the measuring. It is stdlib-only on
purpose: the measurement loop must not depend on numpy's import or allocation
behaviour, and scipy and scikit-learn are broken on that board.

Campaign structure:

- **Calibration.** The payload size `w` is sized so that the median execution
  time on an otherwise-idle board is ~0.45 D. The whole calibration history is
  recorded in `manifest.json`, including the attempts that missed.
- **Probes.** 15 s at each CPU-stressor level 0..6, to choose the long run's
  contention level by a **declared, pre-registered rule**: the level whose probe
  miss rate is closest to 0.02 within the band [0.0005, 0.25], with a
  pre-declared fallback of 4. The rule, the band and the probe rates are all in
  `manifest.json`, so the choice is auditable and was not made after seeing the
  long run.
- **Ground truth run.** 600 s at the chosen level.
- **Nine mixes.** 150 s at each CPU level 0..6, one memory-only mix (2 memory
  stressors), one combined mix (2 CPU + 1 memory).
- A 1 Hz monitor process records, per second, foreign/our/stressor CPU
  occupancy from `/proc/stat` deltas, all six core clocks, `tj-thermal`
  (`thermal_zone8`) and load average.

## Scope, which is part of the result

- One power mode (`MAXN_SUPER`). `sudo -n true` returns non-zero on this board,
  so `nvpmodel` and `jetson_clocks` are unreachable unattended and **every
  figure is a MAXN_SUPER figure.**
- One ambient, never instrumented or varied. Held-out ambient is
  **structurally unmeasurable** from here.
- One CPU-only payload in CPython. Nothing here supports a statement about a
  compiled payload, a GPU payload, or a different period.
- **The board is shared.** Foreign CPU occupancy is measured per second and
  reported; it is measured contamination, not assumed absence.
- One board, with its own heatsink and fan.

Nothing in this product supports a general statement about deadline misses on
Orin Nano.

## Deliverables

Standard product layout. `MODEL_CARD.md` required (AI product). Validation
scripts flat in `validation/`, each anchored on `__file__`, each setting
`sys.dont_write_bytecode = True` first, each runnable from any working
directory. Committed traces under `data/traces/`. No absolute path in any
tracked file. Dependencies bounded on both sides at versions actually measured.
