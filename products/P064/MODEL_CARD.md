# Model card: the regressselect learned selector

Version 0.1.0 · 2026-10-15 · status TESTING

**This model is not certified for operational flight use.**

Research-grade software. Not flight-qualified, not certified, not approved for
operational aerospace use.

Every number in this card comes from a script in `validation/` that was run in
the build session. The script is named beside each table.

---

## 1. Problem

Given a code change and a test suite, produce a ranked order over the tests
such that the tests most likely to fail at this change are run first, and
attach to each test a probability that it will fail. The ranking is then
truncated at whatever fraction of the suite the user is prepared to run.

The decision the model is meant to support is: *which tests can this diff
skip*. The decision quality is measured by **safety loss** -- the fraction of
the tests that actually failed which the truncated selection would not have run
-- and by **APFD**, the average percentage of faults detected over the order.

## 2. Baselines, implemented first

Both baselines were implemented and measured before any model was fitted, and
both are scored on the same held-out revisions with the same test universe.

| baseline | mechanism | module |
|---|---|---|
| Baseline 1, dependency | import-graph reachability from changed modules to test modules; selection, not ranking | `regressselect.importgraph` |
| Baseline 2, history | smoothed conditional failure rate `P(test fails \| module changed)`, Jeffreys pseudo-count 0.5, scored as the maximum over changed modules | `regressselect.prioritise` |

A third, no-information control is also reported: the suite in node-id order.

## 3. Architecture

`sklearn.ensemble.GradientBoostingClassifier` over eleven features of a
(change, test node) pair. Default configuration, declared in
`regressselect.selector.SelectorConfig`:

| hyper-parameter | value |
|---|---|
| `n_estimators` | 150 |
| `learning_rate` | 0.1 |
| `max_depth` | 3 |
| `subsample` | 1.0 |
| `random_state` | 20261015 |
| `calibrate` | `False` (optional isotonic `CalibratedClassifierCV`, 3 folds) |

Trees rather than a linear model because three features interact
multiplicatively with distance: the same churn two hops away and four hops away
are different signals, and a shallow ensemble represents that without the
interaction terms being written out. PyTorch is not available in this
environment and is not needed at this data scale.

**No model is serialised or committed.** Training is fast enough to repeat, so
there is no pickle whose format would couple this product to a scikit-learn
patch release.

### Features

| # | feature | unit |
|---|---|---|
| 1 | `n_changed_modules` | count |
| 2 | `log1p_total_churn` | log1p(lines) |
| 3 | `log1p_max_churn` | log1p(lines) |
| 4 | `reachable` | 0 or 1 |
| 5 | `distance_hops` | import-graph hops, 8 when unreachable |
| 6 | `inverse_distance` | `1/(1+hops)`, dimensionless |
| 7 | `log1p_nearest_churn` | log1p(lines) of the nearest changed module |
| 8 | `cofail_max` | probability |
| 9 | `cofail_mean` | probability |
| 10 | `test_base_failure_rate` | probability |
| 11 | `name_overlap` | fraction in [0, 1] |

Churn is `log1p`-transformed because churn in lines is heavy-tailed and an
untransformed tail dominates a tree split threshold. Unreachable is encoded as
a capped distance *and* as a separate flag, so "far" and "no path" remain
distinguishable.

## 4. Dataset, and its limitations

`fixtures/history/history.json`, 320 revisions over 24 test nodes, seed
20261015. See `DATASET_CARD.md` for the full description. The limitations that
bear on every number below:

- **The history is synthetic.** It is generated by
  `fixtures/regenerate_fixtures.py` from the bundled sample project's *real*
  import graph plus a declared fault-proneness, churn, flakiness and
  out-of-closure coupling model. It is not a mined history of a real
  repository. Any claim about how this model would behave on a real repository
  is unsupported by the evidence in this repo.
- **The suite is 24 test nodes.** A 24-node universe makes rank-based metrics
  coarse: one position is 1/24 of the order.
- **The generator's own structure is part of what the model learns.** Failures
  are drawn with probability decaying in import distance, so a model that
  learns distance is partly learning the generator. That it *does not* lean on
  distance (section 7) is therefore the more interesting observation.
- **Two declared noise channels** -- out-of-closure coupling 0.010 and
  flakiness 0.003 per test per revision -- put a floor under every strategy's
  safety loss, including the dependency baseline's.

## 5. Training procedure and test-split strategy

Split is **chronological**, never random: the first 70 per cent of revisions by
position train, the last 30 per cent are held out. A random split would let the
model see a revision's neighbours and would inflate every number here.

The co-failure estimator that supplies features 8, 9 and 10 is fitted on the
**training slice only**, inside `LearnedSelector.fit`, so no held-out outcome
reaches the features. Baseline 2 is fitted on the same slice, so the comparison
is at equal information.

| quantity | value | source |
|---|---|---|
| training revisions | 224 | `validate_benchmark_output.txt` |
| held-out revisions | 96 | `validate_benchmark_output.txt` |

| training rows | 5376 | `validate_benchmark_output.txt` |

### The verdict, unsoftened

**Baseline 1 wins.** It has the highest APFD, the lowest safety loss at matched
cost, and on the seeded faults it finds every detectable fault while running a
quarter of the suite. The learned selector beats the history baseline on APFD
and on safety loss at every budget, so it is not a no-op -- but it does not
beat the safe baseline, and on this evidence it should not be used in place of
it. The honest recommendation is Baseline 1 for selection, with the learned
ranking used only to order the tests *inside* a dependency-based selection,
which is a configuration this release does not implement.

## 7. Uncertainty and confidence output

The model exposes `LearnedSelector.probabilities(revision)`, the class-one
probability per test node, and `rank()` carries that probability on every
`RankedTest`. It is a score; whether it is a calibrated probability is measured
rather than claimed.

| quantity | value | source |
|---|---|---|
| Brier score, training slice | 0.025500 | `validate_benchmark_output.txt` |
| Brier score, held-out slice | 0.061151 | `validate_benchmark_output.txt` |
| base rate of positives, training | 0.0621 | `validate_benchmark_output.txt` |

The held-out Brier score is 2.4 times the training score. The probabilities are
over-confident out of sample and should be read as a ranking score, not as a
probability to threshold on. `SelectorConfig(calibrate=True)` wraps the
estimator in isotonic calibration; that path is exercised by the test suite but
is not the configuration any number in this card was measured at, and no
calibration improvement is claimed here because none was measured.

## 8. Failure cases

1. **A one-line change.** Feature importances (below) show the model keys on
   churn. On the seeded faults, every one of which is a genuine one-line
   mutation, the learned selector reaches 0.8000 of detectable faults at a
   25 per cent budget; presenting the same faults as 20-line changes lifts that
   to 1.0000. The case where selection matters most -- a small fix to a large
   suite -- is where the model is weakest. Measured in
   `validate_mutation_output.txt`, both churn settings reported.
2. **It ignores the dependency structure.** Combined importance of
   `distance_hops`, `inverse_distance` and `reachable` is **0.0061**. The model
   is almost entirely a churn-and-co-failure model, which is the mechanical
   reason it is less safe than the baseline that uses nothing but dependency
   structure.
3. **A green training history.** `fit` raises `ValueError` rather than fitting
   a degenerate classifier, and the message says to use a baseline.
4. **A test node the history has never seen.** It receives the smoothed base
   rate, so it is ranked near the bottom. A newly added test is therefore
   systematically deprioritised, which is the wrong direction for a new test.
5. **Flaky failures.** The fixture history declares a flake rate of 0.003 per
   test per revision. No selector can be safe against a failure that is not
   caused by the change, and this one is not.
6. **Fixture coupling.** Neither baseline nor the model sees a dependency that
   runs through a `conftest.py` fixture unless the graph is built with
   `with_conftest_coupling()`. On this repository's own suite, the import-only
   selection for `regressselect.features` misses 0.5455 of the test modules
   that actually depend on it. Measured in
   `validate_self_selection_output.txt`.

## 11. Ethical and safety limits

- **This model is not certified for operational flight use.** It decides which
  software tests to run. It does not touch flight software, flight data or any
  operational system, and nothing here is qualified for one.
- Skipping a test on this model's advice can let a regression through. The
  safety loss above is the measured rate at which that happens on the bundled
  fixture, and it is not small: 0.2829 at matched cost. Anyone using this to
  gate a release is accepting that rate, and the release-gating use is not
  recommended by the evidence in this repository.
- The model is trained on which tests failed historically. A test that fails
  often is ranked higher, so a chronically flaky test absorbs budget that a
  reliable test needed. The fix is to deflake the test, not to tune the model.
- No personal data. The history fixture is synthetic and contains no author,
  identity or organisational attribute.
