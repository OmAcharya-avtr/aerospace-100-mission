# Dataset card — `edgeinfer` synthetic model population

**Product:** P033 EdgeInfer · **Package version:** 0.1.0 · **Date:** 2026-10-04
**Validation level:** 3, hardware-pending · **Status:** TESTING

---

## 1. What this is

A population of small ONNX graphs, generated by committed code from a fixed
seed, used to train and evaluate the predictors described in
[`MODEL_CARD.md`](MODEL_CARD.md). Each record is one graph plus the latency
measured for it on the host described in §6.

**Nothing was downloaded.** The `onnx` package is not installed in the target
environment, so the graphs are built by `edgeinfer.onnx_io`, which writes ONNX
ModelProto bytes with a hand-written protobuf codec whose field numbers are
verified against models shipped inside the installed `onnxruntime` wheel.

## 2. How to regenerate it

```python
from edgeinfer.dataset import generate_population
models, summaries = generate_population(n_models=120, seed=20260401)
```

Byte-identical for a given seed. `tests/test_regression.py` pins the SHA-256 of
the concatenated model bytes
(`4c61fd3d8f3e6d9fa4a1278e5531621edb1ec15d7bb7f44bd45b0b5cac32c48f`), every
analytic total and the full feature matrix, so a change to the generator shows
up as a test failure.

Determinism comes from `numpy.random.default_rng`, whose PCG64 bit stream NumPy
guarantees stable across releases for `Generator`.

## 3. Not committed, and why

The 120 serialised models come to **46.2 MB**, above the 1 MB threshold this
programme sets for committing generated data. They are not in the repository.
Regeneration is deterministic and costs **0.31 s** on one CPU core, so there is
nothing to gain from storing them.

## 4. Composition

| Property | Min | Median | Max |
|---|---|---|---|
| nodes per graph | 3 | 6 | 11 |
| floating-point operations | 1 658 | 360 848 | 38 885 406 |
| compulsory traffic [B] | 3 732 | 574 740 | 4 643 528 |
| analytic peak memory [B] | 3 408 | 333 970 | 3 566 984 |
| resident weight bytes [B] | 3 200 | 203 588 | 2 854 536 |

Families: **60 MLPs and 60 CNNs**, alternating by index so the split is
balanced by construction.

Operator occurrences across the population: `Gemm` 238, `Relu` 173, `Conv` 125,
`MaxPool` 125, `Reshape` 60, `Sigmoid` 39, `Tanh` 31.

Generation ranges:

| Family | Ranges |
|---|---|
| MLP | 1–3 hidden layers, width 8–512, inputs 8–512, outputs 2–64, activation `Relu`/`Sigmoid`/`Tanh` |
| CNN | 1–3 conv blocks, 2–48 channels, spatial 8–48, kernel 1/3/5, 2×2 stride-2 `MaxPool` after each block, final `Reshape` + `Gemm` |

All tensors are float32 with batch size 1, except the `Reshape` target-shape
initialiser, which is int64 as the ONNX specification requires.

Weights are standard normal scaled by `1/sqrt(fan_in)` (He, Zhang, Ren & Sun
2015 §2.2). Weight *values* do not change the analytic cost and do not change
`onnxruntime` kernel timing for these operators; the scaling exists only to keep
the runtime's outputs finite in a deeper generated network, which
`tests/test_dataset.py::TestGenerators::test_generated_weights_stay_finite_through_the_runtime`
checks.

## 5. The two hand-counted networks

Separate from the population and fixed:

- `hand_counted_mlp()` — `X(1,4) → Gemm(4,6)+b → Relu → Gemm(6,3)+b → Y`.
  42 MACs, 99 FLOPs, 328 B traffic, 204 B weights, 48 B peak activations.
- `hand_counted_cnn()` — `X(1,1,6,6) → Conv(1→2,3×3,pad 1) → Relu →
  MaxPool(2×2,s2) → Reshape(1,18) → Gemm(18,2)+b → Y`. 684 MACs, 1514 FLOPs,
  1832 B traffic, 240 B weights, 576 B peak activations.

Every one of those ten figures is derived by hand in `validation/validate_opcounts.py`
and in the test-comment derivations of `tests/test_ops.py`, and checked at
tolerance 0.

## 6. The label: measured latency

The target variable is the graph's latency through `onnxruntime` 1.29.0's CPU
execution provider, `intra_op_num_threads=1`, measured with a `perf_counter`
per-call bracket, **60 timed repeats after 8 warm-up calls**, garbage collection
disabled during the batch. Two labels are recorded per graph and used
separately: **p50** and **p99**.

Measured on:

```
Linux-6.18.44-fc-v64-x86_64-with-glibc2.39 x86_64, 1 CPU core(s) available of
1 logical, shared host, Python 3.13.16, clock perf_counter resolution 1e-09 s
```

a **shared single-CPU-core cloud container** with four sibling build jobs
running concurrently. The whole 120-model campaign costs about 1 s.

## 7. Limitations, which are the point of this card

**It is synthetic and narrow.** Feed-forward MLPs and small CNNs. No
transformers, no recurrent layers, no residual connections or branching beyond a
`Concat`, no quantisation, no dynamic shapes, no batch size above 1, float32
only. A result obtained on this population transfers to another model family
only as a hypothesis.

**It is small.** 120 graphs, 36 held out. Sized to a per-script compute budget
of 180 s on one shared core. A 36-point held-out set makes a p90-of-the-error
figure noisy, which is why the predictor comparison is repeated over five
independent measurement passes rather than reported once.

**The label is noisy, and the noise is structured.** On a shared single core the
p99 label is dominated by scheduler preemption, which has nothing to do with the
graph. The measured p99/p50 ratio across the population has a median near 2 and
reaches far higher on a busy moment. **This is the single largest limitation of
the dataset**: the p99 label is partly a measurement of the container's other
tenants, and it is the direct reason the learned predictor shows no measurable
advantage on that target.

**The label is specific to one runtime on one architecture.** `onnxruntime` CPU
on x86-64. Latencies for these graphs are dominated by the per-call cost of the
Python binding rather than by the models' arithmetic — the smallest graph does
1658 flops and still takes microseconds. A device with a different runtime,
different kernels and a different dispatch cost would produce a different label
for the same graph.

**It is not a benchmark suite.** The graphs are generated to span a range of
operation counts and shapes, not to represent any real workload, GNC or
otherwise. Nothing here is a model anyone would deploy.
