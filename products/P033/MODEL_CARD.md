# Model card — `edgeinfer` latency and memory predictors

**Product:** P033 EdgeInfer · **Package version:** 0.1.0 · **Status:** TESTING
**Validation level:** 3, hardware-pending · **Date:** 2026-10-04

This card covers the two predictors the package ships: the **analytic cost
model**, which is the deterministic baseline, and the **learned random forest**,
which exists to be measured against it.

---

## 1. Problem

Given a model graph and a declared device, predict the inference latency and
peak memory that model will show, before it is loaded onto the device. The
prediction feeds a pass/fail decision against a declared budget, so a wrong
prediction in the optimistic direction is the expensive kind: it passes a
candidate that will miss its deadline.

Two targets are predicted separately because they are used differently:

- **median latency (p50)** — throughput planning, cost estimation;
- **worst-case latency (p99)** — deadline sizing for a control loop. This is
  the one that matters and the one both models are worst at.

Peak memory is predicted too, but see §9: it is exact arithmetic and there is
nothing for a learned model to add.

## 2. Baseline, implemented and validated first

The analytic cost model in `edgeinfer.analytic`:

1. Per-node operation counts and compulsory memory traffic from
   `edgeinfer.ops`, with formulas and sources in §3 of that module's docstring.
2. A roofline time bound per node, `t >= max(F/peak_flops, B/peak_bw)`
   (Williams, Waterman & Patterson 2009, *Comm. ACM* 52(4), 65–76), summed over
   nodes assuming sequential execution with no overlap.
3. Two explicit overhead terms the roofline does not model: a per-node dispatch
   cost and a constant per-inference cost.
4. Peak memory by liveness analysis (Aho, Lam, Sethi & Ullman 2006 §8.4).

The four device parameters — peak compute, peak bandwidth, per-node overhead,
fixed overhead — are either **declared** by the caller, in which case the result
is a pure bound, or **fitted** on a training split by `calibrate_device`, in
which case the model's `source` reads `calibrated-fit` and no report can present
it as a datasheet figure. The fit is a grid search over the two peaks (the
objective contains a `max` and is not differentiable at the ridge) with a
non-negative least-squares solve for the two linear terms (Lawson & Hanson 1974
ch. 23, via `scipy.optimize.nnls`), on rows weighted by `1/t_measured` so the
objective approximates relative error.

**This is a four-parameter fit.** It is stated as such everywhere, so that the
comparison against the learned model is between two fitted models rather than
between a fitted model and a fixed formula.

## 3. Architecture of the learned model

`sklearn.ensemble.RandomForestRegressor`, 120 trees, `max_depth=8`,
`min_samples_leaf=2`, `n_jobs=1`, fitted on `log10(target)`.

- **Log target**, because latency spans orders of magnitude across the
  population and a squared-error fit on raw seconds would be decided by the
  largest graph alone. Predicting the logarithm makes the loss a relative error,
  which is what a budget margin is expressed in.
- **A forest**, because the target has thresholds in it — the roofline ridge, a
  cache capacity, a kernel-selection switch inside the runtime — that a linear
  model cannot represent, and because the population is a few hundred points,
  too small for anything with many parameters.
- **One core**: `n_jobs=1`. On the shared single-core host this package was
  built on, more workers cost more than they save.

## 4. Features

17 features, all derived from tensor shapes and operator types with nothing
executed, so a prediction is available before a candidate is loaded. In order:
`log10_flops`, `log10_bytes`, `log10_macs`, `log10_intensity`, `n_nodes`,
`log10_max_node_flops`, `log10_weight_bytes`, `log10_peak_act_bytes`,
`n_distinct_ops`, and the fraction of total flops in each of eight operator
groups (conv, matmul, pool, cheap activation, transcendental activation, binary,
norm, shape).

`log10(x + 1)` is used rather than `log10(x)` so a zero-flop graph maps to 0
rather than `-inf`.

**The features are the same quantities the analytic model uses, plus the
composition of the graph.** That is deliberate: if the learned model wins, it
won by combining the same information better, not by seeing more of it.

A graph containing an operator with no cost rule is **refused** at featurisation
rather than featurised as zero (see `UnsupportedOperatorError`).

## 5. Dataset

See [`DATASET_CARD.md`](DATASET_CARD.md). In short: 120 synthetic ONNX graphs
generated by committed, seeded code; 60 MLPs and 60 small CNNs; 3 to 11 nodes;
1.7e3 to 3.9e7 flops; float32, batch 1. The target is the model's measured
latency through `onnxruntime`'s CPU execution provider on the host described in
§11. **Nothing was downloaded.**

## 6. Training procedure

```bash
python validation/validate_predictor.py
```

- Population: `generate_population(120, seed=20260401)`.
- Measurement: 60 timed repeats after 8 warm-up calls per model,
  `perf_counter` per-call bracket, garbage collection disabled during a batch.
- Split: `split_indices(120, test_fraction=0.30, seed=20260401)` →
  84 train, 36 held out. Identical across runs.
- The analytic baseline's four parameters are fitted **on the training split
  only**, grid 20×20.
- The forest is fitted on the training split only, `random_state=20260401`.
- The whole measure–fit–compare cycle is repeated **five times** from scratch,
  because a measured latency on a shared core is not a fixed quantity and a
  single comparison establishes only which model was better on one pass.

Training cost: 0.142 s for 120 trees on 120 rows; calibration 0.011 s for 400
NNLS solves; the whole eight-script validation suite runs in under 40 s.

## 7. Test-split strategy

A single random 70/30 split with a fixed seed, held out from both the
calibration and the forest fit. No cross-validation and no hyperparameter
search: the hyperparameters are the package defaults and the calibration grid
size is declared in the script, so the held-out set was used exactly once per
pass to measure and never to choose.

The split is **random over graphs**, not stratified by family or by size. With
60 MLPs and 60 CNNs the split lands close to balanced, but a reader should not
read a per-family result out of these numbers.

## 8. Metrics

Median and 90th-percentile absolute relative error — the error's own tail is
reported separately for the same reason the latency's tail is — plus Spearman
rank correlation (the first use of a predictor is ranking candidates) and RMSE
in `log10` space. The comparison between the two predictors is a **paired
bootstrap over the held-out points**, 2000 resamples, seed 20260401; when zero
lies inside one standard deviation of the difference, the verdict is **no
measurable advantage** and no advantage is claimed.

## 9. Results

Five independent passes, held-out set, median absolute relative error:

| Target | learned wins | analytic wins | no measurable advantage | analytic range | learned range |
|---|---|---|---|---|---|
| median latency (p50) | **5/5** | 0/5 | 0/5 | 21.20 – 24.96 % | 8.42 – 15.20 % |
| worst-case latency (p99) | 0/5 | 0/5 | **5/5** | 30.55 – 43.71 % | 33.49 – 51.25 % |
| peak memory | 0 | **exact** | — | 0.00 % by construction | 11.17 % median, 62.65 % p90 |

Single recorded pass, for the p90 of the error and the rank correlations:

| Target | analytic median | learned median | analytic p90 | learned p90 | analytic ρ | learned ρ |
|---|---|---|---|---|---|---|
| p50 latency | 25.08 % | 16.95 % | 46.16 % | 43.66 % | 0.9243 | 0.9593 |
| p99 latency | 22.80 % | 45.58 % | 86.58 % | 108.57 % | 0.8332 | 0.8489 |

**Read plainly:**

- On **median latency the learned model wins**, consistently and by a wide
  margin: 8–15 % against 21–25 %.
- On **worst-case latency neither model wins.** Every pass returned *no
  measurable advantage*. Both are poor in absolute terms. The tail on a shared
  host is dominated by scheduler preemption, which is a property of the machine
  rather than of the model graph, so no graph feature predicts it. A different
  host, or a device with a real-time scheduler and no co-tenants, could give a
  very different answer — and that is one of the measurements this product does
  not have.
- On **peak memory the analytic model wins outright.** It is integer arithmetic
  over the graph's tensor shapes plus a liveness analysis; its error against
  itself is zero. A forest trained on the same population with the two memory
  features ablated reached 11.17 % median and 62.65 % p90 error, and it needs
  the population to have been measured first. **Shipping a learned memory
  predictor would be strictly worse than the arithmetic, and this card says so
  rather than shipping one as a feature.**

No retuning was done to change any of these outcomes. The analytic model was
written and validated before the learned one.

## 10. Uncertainty output, and its measured coverage

Every learned prediction carries an uncertainty: the standard deviation of the
per-tree predictions, propagated from `log10` space by the GUM first-order
sensitivity coefficient `u(y) = y ln(10) u(log10 y)` (JCGM 100:2008 §5.1.2).
Breiman 2001 relates ensemble spread to the variance component of a forest's
error.

**It is not a calibrated prediction interval, and the gap is measured rather
than disclaimed.** On the held-out set:

| Target | median relative spread | truth inside ±1 u | truth inside ±2 u |
|---|---|---|---|
| p50 latency | 34.3 % | 75.0 % | 91.7 % |
| p99 latency | 53.8 % | 72.2 % | 86.1 % |

A calibrated Gaussian interval would give about 68 % and 95 %. The ±2 u coverage
is short on both targets, because the spread measures disagreement between trees
and not the irreducible measurement noise. Use it to rank which predictions to
distrust, not as a confidence interval.

The analytic model's uncertainty is of a different kind and is stated
differently: it is a *bound* when both overhead terms are zero, and a fit with
four free parameters when they are not. Neither carries a probabilistic
interval.

Everything in this card was produced on a **shared cloud container with one CPU
core and 7.8 GiB of RAM**, with four sibling build jobs running concurrently:

```
Linux-6.18.44-fc-v64-x86_64-with-glibc2.39 x86_64, 1 CPU core(s) available of
1 logical, shared host, Python 3.13.16, clock perf_counter resolution 1e-09 s
```

plus five stability passes), runs in **9 s**. No GPU, no accelerator, nothing
downloaded.

## 12. Failure cases

- **A graph with an unsupported operator** is refused, not predicted. The
  analytic model raises `UnsupportedOperatorError` and the featuriser does the
  same, because an unknown operator charged zero cost turns a budget overrun
  into a budget pass.
- **A graph outside the training distribution.** The forest is a piecewise
  constant function of its features; outside the training support it returns the
  nearest leaf's mean and its ensemble spread widens, which is the only warning
  it gives. A transformer, an RNN, a quantised graph or a model two orders of
  magnitude larger is outside everything this card covers.
- **The worst case.** Covered above: no measurable advantage over the analytic
  baseline on any of five passes, and 31–51 % median error for both.
- **A compute-bound calibration set.** When every node in the calibration set is
  compute bound, the fitted bandwidth is unidentifiable and carries no
  information, although the fit still reproduces the latencies it saw. Asserted
  directly in `tests/test_roofline.py`.
- **A different runtime or device.** The target here is `onnxruntime`'s CPU
  execution provider on x86-64. A fit against TensorRT on an Orin Nano would be
  a different model and would have to be re-validated there.

## 13. Reproducibility

```bash
pip install -e ".[dev]"
python validation/validate_predictor.py        # the full campaign
python -m pytest tests/test_regression.py -q   # pinned seeded outputs
```

Seeds: population 20260401, split 20260401, forest 20260401, comparison
bootstrap 20260401, stability passes seeded `20260401 + pass_index`. Pinned
outputs in `tests/test_regression.py` cover the generated model bytes (SHA-256
of the concatenation), every analytic total, the feature matrix, the calibration
fit on fixed synthetic data, the split indices and the forest's predictions.
Latencies are deliberately **not** pinned: they are host-dependent and pinning
them would be pinning the container's load.

## 14. Ethical and safety limits

This model predicts the resource cost of running another model. It makes no
decision about people, consumes no personal data and produces no content. The
safety-relevant risk is narrow and specific: **a prediction used to size a
deadline that the deployed model then misses.** The mitigations are structural
rather than advisory —

- the worst case is reported separately from the median everywhere, and a
  verdict follows the worst case;
- a pass by less than two combined standard uncertainties is reported as
  `MARGINAL PASS`;
- an unsupported operator is refused rather than charged zero;
- a power limit is always `NOT MEASURED`;
- every number carries its measurement method, repeat count and environment.

None of that makes a prediction safe to size a deadline against on a device this
package has never run on.

**This model is not certified for operational flight use.**
