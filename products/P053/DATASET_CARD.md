# Dataset card — twininvalidate synthetic residual streams 0.1.0

**Entirely simulated. No flight data, no hardware, no real asset, no personal
data.** Every array used anywhere in this repository is generated by committed
seeded scripts. No data file is committed, and regeneration is deterministic:
identical `StreamSpec` values give bit-identical streams.

## 1. What the data is

A **normalised residual stream** `z`: the innovation of a fixed-gain
steady-state Kalman filter built from a declared linear-Gaussian twin, divided
by `sqrt(S)` where `S` is the innovation variance. `z` is dimensionless, and
under the in-control hypothesis it is i.i.d. N(0, 1) — the innovations
property (Kailath 1968), measured rather than assumed in
`validation/validate_twin.py`.

One record is one window of 50 consecutive `z` values, reduced to the nine
features of `src/twininvalidate/features.py`.

## 2. Source model

`twininvalidate.twin.reference_twin()`: an illustrative single-axis attitude
channel, **not** any flight vehicle.

| Parameter | Value | Units |
|---|---|---|
| natural frequency `ω_n` | 2.0 | rad/s |
| damping ratio `ζ` | 0.10 | — |
| sample interval `dt` | 0.05 (20 Hz) | s |
| acceleration noise `σ_a` | 0.02 | rad/s² per √Hz |
| measurement noise `σ_meas` | 0.01 | rad |
| innovation variance `S` | 1.165114435e-04 | rad² |
| `sqrt(S)` | 1.079404667e-02 | rad |
| predictor gain `K` | [0.151684, 0.182596] | — |
| spectral radius of `A − KC` | 0.917218 | — |

Discretisation: zero-order hold via the matrix-exponential block form
(Franklin, Powell & Workman 1998). Process noise: the continuous
white-noise-acceleration discrete equivalent (Bar-Shalom, Li & Kirubarajan
2001).

**Excitation.** `u_k = 1.0 + 0.2 sin(2π · 0.15 · k dt)` rad/s² — a constant
command with a small dither below the 0.318 Hz natural frequency. This is not
decoration: a parameter change is only visible in the residual if the asset is
being driven, and the constant part is what makes an actuator-gain change
produce a *constant* residual mean rather than an oscillation.

## 3. Classes and change scenarios

Negative class (label 0): in-control streams, asset obeying the declared twin.

Positive class (label 1): three change kinds, **one magnitude each**, present
from sample 0 of the labelled stream.

| Scenario | Injection | Residual effect (measured) |
|---|---|---|
| `parameter_step` | asset actuator gain steps to 0.99 | mean −0.409, variance 1.002 |
| `slow_ramp` | the same gain ramps to 0.99 over 400 samples (20 s) | mean reaches −0.409 |
| `noise_variance` | asset process-noise covariance × 2 | mean −0.003, variance **1.059**, lag-1 autocorrelation +0.058 |

The parameter-step mean shift has a closed form,
`E[z] = C (I − (A − KC))⁻¹ B δ u₀ / sqrt(S)`, which predicts −0.4043 against a
measured −0.4050 at δ = −0.01, a 0.16 % error
(`validation/validate_twin.py`).

**Note the asymmetry in the noise-variance scenario.** Multiplying the
asset's *process* noise by 2 raises the *residual* variance only to 1.059,
because the measurement noise `R = 1e-4 rad²` dominates the innovation
variance `S = 1.165e-4 rad²`. A reader who assumes "× 2 process noise" means
"× 2 residual variance" will mis-read every number in this repository; this
repository made that mistake once and records it in
`validation/VALIDATION.md`, error 2.

A fourth mechanism, `sensor_offset`, exists only for the attribution
demonstration in `twininvalidate.ambiguity` and is not part of the training
data.

## 4. Size and composition

| Set | In-control runs | Changed runs | Samples/run | Windows | Balance |
|---|---|---|---|---|---|
| Training | 120 | 40 × 3 scenarios | 600 | 13 440 | 0.500 |
| Probability calibration | 60 | 20 × 3 scenarios | 600 | 6 720 | 0.500 |
| Threshold calibration | 200–400 | — | 2000–4000 | — | n/a |
| Evaluation | 200 | 200 per scenario | 2500 | — | n/a |

Windows are subsampled with stride 10 to keep the training set inside the
compute budget. Consecutive windows still overlap in 49 of 50 samples, which
is why every split is **by run**, never by window.

Burn-in: 200 samples are simulated before sample 0 of every returned stream,
so the prediction-error transient has decayed (`0.917²⁰⁰ ≈ 1e-8`).

## 6. Labelling, and its deliberate noise

A window is labelled 1 if the change was active for the whole window, 0
otherwise. For `slow_ramp` with the onset at sample 0 this includes early
windows in which the ramp has barely begun and which are statistically
indistinguishable from in-control.

Those windows are labelled 1 anyway. The alternative — dropping them, or
labelling by an effect-size threshold — would make the training problem easier
than the monitoring problem actually is, and would inflate every reported
score. The consequence is irreducible label noise, which is the main reason
the model's Brier score is 0.1589 rather than something near 0.

A second, unavoidable source: a 50-sample window of the declared parameter
step carries a mean shift of 0.404σ, i.e. about 2.9 standard errors of the
window mean. A window-level decision is genuinely uncertain even with a
perfect model.

## 7. Known limitations

1. **One sign only.** Every gain change is negative. The trained model does
   not detect a positive gain change of the same magnitude: 2 % of runs
   against every baseline's 100 %.
2. **One magnitude per kind.** Nothing in the data tells the model what a
   different magnitude looks like, and its performance degrades on both
   smaller and larger ones.
3. **Three kinds only.** Sensor dropout, quantisation, bias drift, delay,
   intermittency and actuator saturation are all absent.
4. **Perfectly Gaussian and white in control, by construction.** Real residual
   streams are not, and nothing here is validated for one that is not.
5. **Scalar measurement only.** `C` is `(1, n)`.
6. **Stationary excitation.** The same input profile in every run; a real
   asset's excitation varies and detectability varies with it.
7. **No model error other than the injected one.** The twin and the asset
   agree exactly before the onset, which is the most favourable possible
   in-control condition.
8. **Nothing is held out across twins.** Every set comes from the same
   declared channel, so none of the reported numbers is evidence about
   transfer to a different plant.

## 8. Intended and unintended use

Intended: measuring detection delay against false-alarm rate for sequential
detectors on a residual whose in-control distribution is known exactly, and
benchmarking a learned detector against analytic ones on the same streams.

Not intended: training anything to be deployed; estimating any real asset's
failure rate; any claim about a physical vehicle. The probability this data
supports is the probability *of the declared model*.

## 9. Regeneration

```bash
pip install -e ".[dev]"
python -m twininvalidate scenarios        # the declared scenarios
python validation/validate_twin.py        # the residual statistics quoted above
python validation/validate_classifier.py  # regenerates the training sets and fits
```

```python
from twininvalidate import training_set, calibration_set, in_control_streams, changed_streams
train = training_set()                                   # 13 440 labelled windows
cal = calibration_set()                                  # 6 720 labelled windows
bank = in_control_streams(n_runs=400, n_samples=4000, seed=53001)
oc = changed_streams("noise_variance", n_runs=300, n_samples=3000)
```
