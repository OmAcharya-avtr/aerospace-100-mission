# Model card — activityplan duration and energy predictor

**This model is not certified for operational flight use.**

The software around it is research-grade: not flight-qualified, not certified,
and not approved for operational aerospace use.

---

## Problem

Given an activity described by features — type, slew angle, data volume,
instrument temperature, detector gain — predict:

1. its **duration** [s], and
2. its **energy demand** [W\*h],

each with a **prediction interval**, so that an onboard planner can book time and
energy for it before it runs.

Both predictions feed a planner. The duration decides how much of the timeline
the activity occupies and how fast it writes to the recorder; the energy decides
how much the battery has to cover. A prediction that is optimistic in either
direction produces a plan that fails when the activity actually runs, which is
the outcome this model exists to reduce and which
`validation/validate_robust.py` measures directly.

## Baseline, implemented first

The analytic model in `src/activityplan/features.py`, written and validated
before any learned component existed:

```
duration = setup_s
         + slew_angle_deg / slew_rate_deg_per_s
         + settle_s
         + data_mbit / readout_rate_mbit_per_s

power    = base_power_w + power_per_data_rate_w * (data_mbit / duration)
```

Shape from standard slew-settle-collect timeline arithmetic (Wertz & Larson
1999, chapters 2 and 14). Every constant is declared in
`features.TYPE_CONSTANTS` and **none was identified from any spacecraft**.

The learned model is benchmarked against this baseline on the **same held-out
rows**, paired, over five dataset seeds.

## Architecture

- **Point predictor:** `sklearn.ensemble.RandomForestRegressor`, 160 estimators
  in the validation runs (200 is the library default), `min_samples_leaf = 2`,
  `n_jobs = 1`, seeded. One forest per target (Breiman 2001).
- **Interval:** **split conformal prediction**. Fit the forest on a proper
  training set; on a disjoint calibration set of size `n` form nonconformity
  scores; take `q` as the `ceil((n+1)(1-α))/n` empirical quantile; the interval
  is `f(x) ± q`.
  - `mode="absolute"`: scores are `|y - f(x)|`, giving a constant-width interval.
  - `mode="normalised"`: scores are `|y - f(x)| / (s(x) + β)`, where `s` is a
    second forest fitted to the **out-of-bag** absolute residuals of the training
    set and `β` is a positive regulariser. This is the locally weighted variant
    (Papadopoulos et al. 2002; Lei et al. 2018).
- **Why not the forest's own tree-to-tree spread:** it has no coverage guarantee
  (Wager, Hastie & Efron 2014). Split conformal has a distribution-free
  finite-sample marginal guarantee, which is the only kind this package is
  willing to print.
- **When the level is unattainable** — `ceil((n+1)(1-α)) > n`, which happens for
  a small calibration set — the quantile is `+inf` and
  `ConformalRegressor.level_attainable` is `False`. The interval is infinite
  rather than quietly narrower than it should be.

Features, in order (`features.FEATURE_NAMES`):

| # | feature | unit |
|---|---|---|
| 0–3 | one-hot of `image`, `spectro`, `radar`, `calibration` | dimensionless |
| 4 | `slew_angle_deg` | deg |
| 5 | `data_mbit` | Mbit |
| 6 | `instrument_temperature_c` | C |
| 7 | `gain` | dimensionless |
| 8 | `analytic_duration_s` | s |
| 9 | `analytic_mean_power_w` | W |

**Features 8 and 9 are the analytic model's own predictions.** Supplying them
means the learned model fits the *correction* to the baseline rather than
relearning it. **This advantages the learned model by construction** and is
stated here, in `README.md` and in `src/activityplan/features.py` so that the
benchmark is not read as a like-for-like contest.

## Dataset source and limitations

Fully synthetic, generated by committed, seeded code. See
[`DATASET_CARD.md`](DATASET_CARD.md). The generator is
`features.realise`, declared in full in its docstring:

```
d = analytic_duration
  + cold_settle_s_per_10c * max(0, 10 - temperature_c) / 10     (omitted by the baseline)
  + gain_penalty_s_per_mbit * (gain - 1)^2 * data_mbit          (omitted by the baseline)
  + Normal(0, 0.08 * analytic_duration)

p = analytic_power
  + heater_w_per_10c * max(0, 10 - temperature_c) / 10          (omitted by the baseline)
  + Normal(0, 0.03 * analytic_power)
```

**The single most important limitation of this model card.** The learned model
beats the analytic model on this data because the analytic model is **missing two
terms the generator contains**. The size of the win measures a misspecification
this repository declares; it is **not evidence that a learned model would beat a
duration model fitted to a real spacecraft**, and no number here should be read
that way.

What the benchmark *does* measure without that caveat is (a) the calibration of
the prediction interval, which is a property of the conformal construction and of
exchangeability rather than of the generator's realism, and (b) the downstream
effect of prediction error on a plan, which is a property of the planner.

Further limitations: the features are sampled independently, which is
unrealistic — on a real mission instrument temperature correlates with orbital
position and with pointing. There is no temporal structure, no activity-to-activity
correlation and no distribution shift.

## Training procedure

1. Draw `n` requests with `features.sample_requests(n, rng)` over the declared
   validity ranges.
2. Draw one realisation per request with `features.realise(request, rng)`.
3. Build the design matrix with `features.feature_matrix`.
4. `DurationEnergyPredictor.fit(x, duration_s, energy_wh)` splits the rows by a
   seeded permutation into proper-training and calibration parts
   (`calibration_fraction = 0.35` by default), fits both forests on the
   proper-training part and calibrates both on the calibration part.

No hyper-parameter search was run. The forest settings are the library's
defaults with `n_jobs` fixed at 1 and `min_samples_leaf = 2`; `n_estimators` was
reduced from 200 to 160 in the validation scripts to keep every run inside the
three-minute budget, and no setting was chosen by looking at a test score.

## Metrics

From `validation/validate_predictor_output.txt`, five dataset seeds
(61–65), 1400 activities each, 400 held out.

| target | analytic MAE | learned MAE | MAE ratio (mean) | ratio range | irreducible floor | gap closed |
|---|---:|---:|---:|---|---:|---:|
| duration [s] | 31.60685 | **29.12174** | **0.9249** | 0.8641–0.9968 | **26.74746** | 51.1 % |
| energy [W\*h] | 1.00330 | **0.40974** | **0.4116** | 0.3646–0.4591 | **0.31358** | 86.1 % |

RMSE is in the committed output per seed; at seed 61 it is 49.91145 s analytic
against 46.60061 s learned for duration, and 1.90834 against 0.61294 W\*h for
energy.

**The floor matters.** The generator's duration noise is
`Normal(0, 0.08·analytic_duration)`, so the best achievable MAE for any predictor
is the mean of `σ·sqrt(2/π)` over the test set: **26.74746 s** in closed form,
cross-checked by 200-draw Monte Carlo at **26.83000 s** (relative difference
0.0031). The learned model closes **51.1 %** of the distance between the analytic
model and that floor on duration and **86.1 %** on energy. Read against zero the
duration improvement looks small; read against the floor it is half of what was
available.

## Test-split strategy

- **Proper-training / calibration split**: a seeded permutation of the fitting
  rows, 65 % / 35 % by default. The two are disjoint, which is what the conformal
  guarantee requires.
- **Held-out test set**: 400 further activities drawn from the same declared
  sampler, never seen by either forest or by the calibration step.
- Every split is reproducible from the integer seeds in the scripts; there is no
  environment variable and no configuration file.
- **No model selection was performed on the test set.**

## Uncertainty output

A two-sided interval per target per activity, from split conformal prediction.

**Marginal coverage: attained.** Over 12 combinations of level (0.05, 0.10, 0.20)
× mode (absolute, normalised) × target (duration, energy), **none** falls below
nominal by more than three binomial standard errors at n = 400. At α = 0.10 on
duration: absolute **0.8820**, normalised **0.9025**, against a nominal 0.9000.

**Conditional coverage: not attained, and not guaranteed.** By tercile of the
analytic duration, at α = 0.10:

| mode | short | middle | long |
|---|---:|---:|---:|
| absolute | 1.0000 | 0.9669 | **0.6782** |
| normalised | 0.9343 | 0.9053 | **0.8677** |

The constant-width interval covers the longest third of activities **0.6782** of
the time against a nominal 0.90. That is not an implementation defect: split
conformal guarantees marginal coverage and nothing more, and the generator's
noise scales with duration by declaration. The normalised variant reduces the
shortfall from **0.2218** to **0.0323** and does not remove it.

**Consequence for use:** the interval is a statement about a population of
activities, not about the activity in front of you. It must not be reported as a
per-activity confidence statement.

## Failure cases

1. **The two intervals are not jointly calibrated.** The probability that both
   the duration and the energy interval cover is not `1 - α`; the only bound this
   package can state is the union bound `1 - 2α`.
2. **Conditional coverage fails on long activities**, as measured above. A long
   activity's interval is systematically too narrow in the constant-width mode.
3. **Planning against the interval's upper bound makes plans worse.** Measured in
   `validation/validate_robust_output.txt`: the `ml-robust` mode achieves
   **0.4167** realised feasibility against the `ml-point` mode's **0.4722**, and
   **11.333** against **12.472** realised priority units, over 36 plans each.
   The mechanism is structural and is measured: an activity's **data volume is
   declared, not predicted**, so its production rate is volume over duration.
   Booking the conformal upper bound on duration books a **lower** production
   rate; the realised duration is shorter, the real rate is higher, and the
   recorder overflows. `ml-robust` underbooks the rate on **99.40 % (0.9940)** of
   activities, with a mean realised/planned rate ratio of **1.1911**, and **all
   21** of its infeasible plans fail on `recorder-capacity` and nothing else.
   **Planning against an upper bound on duration is conservative for time and
   energy and anti-conservative for the recorder.**
4. **The warm start does not help the solver.** On **31 of 34** cold solves HiGHS
   closes the gap at the root node, so a primal bound has nothing to prune. On
   the one sampled instance that does branch, the learned bound reduced nodes
   from **613 to 510** and *increased* the wall clock from **3.460 s to
   4.380 s**. The learned predictor's measurable contribution to the warm start
   is that its candidate plan verifies as feasible on the target problem **8
   times out of 8**, against **5 of 8** for a plan built from the analytic model
   — and the safety that provides comes from the verification gate in
   `warmstart.warm_start_from_plan`, not from the model.
5. **Extrapolation is not supported.** Outside the declared validity ranges
   (`slew_angle_deg` 0–90, `data_mbit` 10–800, `instrument_temperature_c` -30–35,
   `gain` 0.6–1.8) a random forest returns the nearest leaf's mean, with no
   indication that it is extrapolating. The conformal interval does not widen.
6. **Distribution shift voids the guarantee.** Conformal coverage requires
   exchangeability between calibration and test. Any change in the activity mix
   between calibration and flight removes the guarantee entirely.

## Reproducibility

Exact commands and seeds:

```bash
pip install -e ".[dev]"

# Metrics, coverage and the tercile breakdown (seeds 61-65 are literals)
python validation/validate_predictor.py

# The warm-start study (predictor seed 61, instance seeds 9000+)
python validation/validate_warmstart.py

# The four planning modes under realised durations (predictor seed 61,
# instance seeds 9000-9011, three realisations each)
python validation/validate_robust.py

# The README's worked example, predictor seed 61, held-out requests at seed 99
python validation/worked_example.py

# The figures
MPLBACKEND=Agg python examples/prediction_intervals.py
MPLBACKEND=Agg python examples/robust_tradeoff.py
MPLBACKEND=Agg python examples/warmstart_nodes.py

# The CLI view
python -m activityplan predict --n-train 900 --n-test 300 --mode normalised
```

Every seed is a literal in the script that uses it. Each validation script
writes its raw output beside itself as `<script>_output.txt`, which is committed.

Environment the committed numbers were produced in:

```
python 3.13.16 · numpy 2.5.3 · scipy 1.18.1 · scikit-learn 1.9.1
matplotlib 3.11.2 · pytest 9.1.1 · hypothesis 6.169.3 · 2 CPU cores
```

**The declared dependency ranges are pinned to the minor version executed**
(`scikit-learn>=1.9.1,<1.10`). This package commits no pickled model artifact, so
the unpickling hazard that broke another product in this mission does not apply;
the bound is still pinned because the metrics above would move with a different
forest implementation even if every test still passed.

## Ethical and safety limits

- **This model is not certified for operational flight use.**
- It must not be used to decide whether a real spacecraft activity will fit in a
  real resource budget. It is fitted to a synthetic generator that this
  repository declares in full, and its advantage over the analytic baseline is a
  direct consequence of that generator's declared misspecification.
- Its interval must not be presented as a per-activity confidence statement. The
  guarantee is marginal; conditional coverage is measured here and fails.
- A plan built from its predictions is feasible **with respect to the predicted
  durations and energies**. The feasibility report in
  `activityplan.feasibility` is the only thing in this package that states
  feasibility with respect to a declaration, and it is the artifact to put in
  front of a reviewer.
- Nothing in the package or the model was identified from any spacecraft,
  instrument or mission.
