method
==============================================================================
enumeration: every activity is assigned one admissible start step or not placed,
so the candidate count is prod_i (|starts_i| + 1). Each candidate is tested with
activityplan.feasibility.evaluate, which runs the resource SIMULATOR. The MILP
shares no code with that path beyond the rasterised arrays.

==============================================================================
the defect this check found during the build
==============================================================================
An earlier draft of activityplan.feasibility treated the aggregate downlink
volume -- total data produced against total declared contact capacity -- as a
hard constraint. The MILP never had that constraint. On the four-activity
instance below the MILP returned 6.5 priority units and the enumeration 5.0.
The MILP was right: data left on the recorder at the horizon is not an
infeasibility unless require_empty_recorder is declared. Both readings are
now reproduced, and the instance is pinned in tests/test_regressions.py.

  require_empty_recorder=False enumeration 6.50 milp 6.50
  require_empty_recorder=True  enumeration 5.00 milp 5.00
