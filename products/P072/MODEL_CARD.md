# Model card — downlinkpick learned components 0.1.0

**This model is not certified for operational flight use.**

Two learned components ship in this package. They are documented together
because they feed the same decision and are measured through the same solver,
but they are independent models with separate training tables, separate feature
sets and — as the measurements show — opposite verdicts against their baselines.

| | Value model | Compressibility model |
|---|---|---|
| Module | `downlinkpick.valuemodel.ValueModel` | `downlinkpick.compress.CompressibilityModel` |
| Predicts | realised value of a data product, in value units | compression ratio (compressed/raw), dimensionless |
| Estimator | `sklearn.ensemble.RandomForestRegressor`, 300 trees | `sklearn.ensemble.RandomForestRegressor`, 200 trees |
| Features | 10, `downlinkpick.dataset.VALUE_FEATURES` | 7, `downlinkpick.dataset.COMPRESSION_FEATURES` |
| Verdict against its baselines | **loses to a complete, fresh declaration; wins when declarations are stale or absent** | **wins against every baseline measured** |

## The problem

A downlink selection is only as good as the numbers it is given.

The **value model** exists because a real recorder inventory contains products
nobody declared a value for — an autonomously triggered acquisition, a product
from an instrument whose team was not consulted, a declaration written at
acquisition and never revisited. The exact solver has nothing to say about a
missing value, and a planning tool that silently substitutes zero will never
downlink those products at all.

The **compressibility model** exists because the selection is made against
*estimated* sizes. Under-estimate and the pass overflows: it runs out of time
and the product that did not fit, plus everything queued behind it, is lost.
Over-estimate and the pass ends with capacity unspent.

## Baselines, implemented first

The classical baselines were implemented and measured before either model was
written, and they are what the models are scored against on the same held-out
products and through the same solver.

Value:

- **declared-value passthrough** (`declared_values`), with an explicit fallback
  for missing declarations: the median of the declarations that exist, their
  mean, or zero. All three are measured.
- **a fitted size/age heuristic** (`fit_size_age_heuristic`),
  `value = a + b log10(bytes) + c age_s` by ordinary least squares. Fitted
  rather than guessed, so the comparison is against the best version of the
  simple idea.

Compressibility:

- **the memoryless entropy floor** `min(H/B, 1)`, Shannon's source-coding bound
  for an i.i.d. source. Needs no training data at all.
- **a per-instrument constant table**, the mean realised ratio of each
  instrument's products. This is what a mission database holds.
- **a global mean ratio**, the crudest usable estimator.

## Architecture

Both are random forests of unrestricted depth with `min_samples_leaf=2`,
`random_state=20261021` and `n_jobs=1`. No gradient boosting, no neural network;
PyTorch is not available in the measured environment and would be the wrong tool
for a few thousand rows of tabular data in any case.

Value-model features, in column order:
`log10_raw_bytes`, `age_s`, `time_to_expiry_s`, `novelty`, `coverage_fraction`,
`entropy_bits_per_sample`, `bit_depth`, `channels`, `n_dependents`,
`instrument_code`.

Compressibility features:
`entropy_bits_per_sample`, `bit_depth`, `entropy_ratio`, `lag1_autocorr`,
`log10_raw_bytes`, `channels`, `instrument_code`.

The value model deliberately does **not** take the declared value as a feature.
Its job is to predict value where no declaration exists, and a model that
depended on one would be useless in exactly that case. Combining the two is the
caller's decision and is exposed as `hybrid_values`, which keeps every
declaration and fills only the gaps.

## Dataset

Synthetic, generated by `src/downlinkpick/dataset.py` from fixed seeds. See
`DATASET_CARD.md` for the generating equations, the sampling distributions and
the limitations. The headline limitation is unavoidable and is repeated here:

> **No real spacecraft recorder inventory, contact plan or codec is used
> anywhere in this repository.** Every number in this card is a statement about
> the generator in `downlinkpick.dataset`, whose equations are printed in that
> module's docstring. Nothing was fitted to flight data because this build had
> none.

A latent per-product "site weight" enters the true value of equation (3) and is
**not** a feature of any model here, so it is the irreducible error floor of
every value estimator measured.

## Training procedure

| | Value model | Compressibility model |
|---|---|---|
| Table | 6000 products, seed 1001 | 6000 products, seed 1002 |
| Split | first 70 per cent train, last 30 per cent test (4200 / 1800) | 4200 / 1800 |
| Target | realised value, equation (3) | realised ratio, equation (7) |
| Fit time | 3.886 s | 1.876 s |

## Test-split strategy

Two levels, because there are two questions.

**Regression accuracy** is measured on the held-out 30 per cent of the training
table: products the model never saw, drawn from the same generator.

**End-to-end regret** is measured on instances generated from a *different seed
stream* — seeds 5001 to 5030 for the value model and 6001 to 6030 for the
compressibility model — so no product in the benchmark appears in the training
table. The instances also carry a dependency graph and a contact plan, which the
flat training table does not, so the benchmark exercises the model on structures
it was not trained against.

## Metrics

### Value model, regression on 1800 held-out products

| Estimator | MAE | RMSE | Spearman | bias |
|---|---|---|---|---|
| learned forest | 0.962341 | 1.585054 | 0.912832 | 5.278e-03 |
| size/age fitted | 1.863225 | 2.561772 | 0.557234 | 4.825e-03 |
| train mean | 2.233730 | 3.034266 | nan | 5.277e-02 |

The `nan` is not a reporting artefact: a constant vector has no ranks.

### Value model, end-to-end regret through the exact solver

`regret = oracle selection value - arm selection value`, both scored on the
ground-truth values, 30 instances per scenario, 24 products over 3 windows.

| Scenario | declared-median | size-age | learned | hybrid | best |
|---|---|---|---|---|---|
| 1 complete and fresh | **0.000404** | 0.039722 | 0.009582 | 0.000404 | declared |
| 2 complete but stale | 0.015860 | 0.039722 | **0.009582** | 0.015860 | learned |
| 3 30 per cent missing | 0.015418 | 0.036017 | 0.005488 | **0.002253** | hybrid |
| 4 all missing | 0.986665 | 0.042048 | **0.008156** | 0.008156 | learned |
| 5 40 per cent missing, half stale | 0.021350 | 0.036160 | **0.005799** | 0.009625 | learned |

**The specification predicted that the exact solver on declared values would
beat everything and that the learned value model would help only where
declarations are absent. That is what was measured, with one refinement, and it
is published as the result.** The declared-value passthrough is the best arm in
scenario 1 and in no other. The refinement is that the learned model also helps
where declarations are *stale* rather than only where they are missing, which
the specification's own wording anticipated.

The collapse in scenario 4 is worth stating plainly: with no declaration
anywhere, both fallbacks reduce to zero, the passthrough has no information at
all, and its regret fraction is **0.986665** — it delivers essentially nothing
of value. That is the case the learned model exists for.

The ranking is a property of the estimators, not of the solver: through the
greedy baseline on scenario 5 the ordering is identical.

## Uncertainty and confidence output

Both models expose the standard deviation of their per-tree predictions
alongside the ensemble mean: `ValueModel.predict_with_dispersion`,
`CompressibilityModel.predict_with_dispersion`, and the `RatioPrediction` and
`ValuePrediction` dataclasses.

**This is a dispersion measure over the ensemble and not a calibrated confidence
interval.** The trees share training data, so the spread understates predictive
uncertainty (Wager, Hastie and Efron 2014). Measured coverage of the bands:

| Band | Nominal Gaussian | Value model | Compressibility model |
|---|---|---|---|
| +-1 sigma | 0.6827 | 0.688889 | 0.590000 |
| +-1.96 sigma | 0.9500 | 0.941111 | 0.878333 |
| +-2 sigma | 0.9545 | 0.947222 | 0.885000 |

The value model's band is close to nominal; the compressibility model's is
visibly narrow. Neither is calibrated and neither should be used as one.

The dispersion is nonetheless informative about *where* the model is wrong,
which is its operational use: the rank correlation between the dispersion and
the absolute error is **0.601302** for the value model and **0.495530** for the
compressibility model. A product the ensemble disagrees about is a product to
look at by hand before spending a pass on it.

**One place the uncertainty changes a decision rather than annotating one.**
`RatioPrediction.conservative` is `ratio + 2 sigma`, the size estimate to plan
with when an overflow costs more than unspent capacity. Measured, it removes
every overflow (0.000000 against 0.144444) at a cost of 6.9 points of unspent
capacity, and delivers *more* value overall (0.962760 against 0.947669), because
an overflow loses not only the product that did not fit but everything queued
behind it in that pass.

## Failure cases

- **The value model is beaten by a fresh, complete declaration**, by a factor of
  24 in regret fraction. If your declarations are current, do not use it.
- **The value model cannot recover the latent site weight**, which is a genuine
  component of the true value in the generator and is not a feature. Its error
  floor is set by that term and no amount of training data removes it.
- **Both models are trained on one generator** and nothing establishes that a
  real inventory resembles it. A new instrument class, a different value scale,
  or a codec that behaves unlike equation (7) is out of distribution and the
  models have no way to signal that beyond a wide ensemble dispersion.
- **The compressibility model's +-2 sigma band covers 0.885 of held-out
  products**, so the conservative size estimate under-reserves for roughly one
  product in nine. It removed every overflow on the 30 benchmark instances; that
  is a measurement on 90 windows, not a guarantee.
- **The entropy floor is not a lower bound for a correlated source.** 0.997778
  of held-out products compress below it. Anyone treating `H/B` as a hard floor
  in a capacity reservation will over-reserve by about 65 per cent.
- **Neither model is the selector.** They supply numbers to an optimiser; a bad
  value estimate that preserves the *ranking* costs nothing, and a small error
  that crosses a selection boundary costs a whole product. Regression error is
  not a proxy for either.
- **A product with no declaration and a wide ensemble spread is the worst case**
  and the package surfaces it rather than hiding it: on the shipped
  `missing_declarations` case the widest spread is `msi-001` at +-1.858 value
  units against a learned value of 4.9798.

## Reproducibility

Exact commands and seeds, from the repository root after `pip install -e ".[dev]"`:

```bash
# the value model: training table seed 1001, model seed 20261021,
# benchmark instances seeds 5001..5030
python validation/validate_valuemodel.py

# the compressibility model: training table seed 1002, model seed 20261021,
# benchmark instances seeds 6001..6030
python validation/validate_compress.py

# the worked example, which trains both on the 6000-row table from seed 1001
python validation/worked_example.py

# the figures
MPLBACKEND=Agg python examples/value_model_benchmark.py
MPLBACKEND=Agg python examples/compressibility_benchmark.py
```

Each writes its raw output to `validation/<script-name>_output.txt`. Every
random draw in this package goes through a seeded
`numpy.random.default_rng(numpy.random.SeedSequence([...]))` or through
scikit-learn's `random_state`, and the model fits are reproducible: two
`ValueModel(seed=5)` fits on the same table give bit-identical predictions,
which is asserted in `tests/test_valuemodel.py`.

## Compute used

Measured on the 2 shared cores of the build container. **Wall clock, unstable
between runs, recorded for the budget and supporting no conclusion.**

| Step | Wall clock |
|---|---|
| Value model fit, 300 trees on 4200 rows x 10 features | 3.886 s |
| Compressibility model fit, 200 trees on 4200 rows x 7 features | 1.876 s |
| Value-model benchmark, 5 scenarios x 6 arms x 30 instances | 54.716 s |
| Compressibility benchmark, 6 arms x 30 instances | 7.624 s |

No training, sweep or benchmark in this repository approaches the three-minute
budget the mission imposes on a single run. No GPU is used or required; PyTorch
is not installed and is not a dependency.

## Ethical and safety limits

- **This model is not certified for operational flight use.** It is
  research-grade software, not flight-qualified, not certified, and not approved
  for operational aerospace use.
- **No output of this package should be used to decide what a spacecraft
  transmits without a human in the loop.** The value model predicts what a
  value *would have been declared as*; it does not know why a product matters,
  and a product whose value is low by the generator's reckoning may be the one
  an operator needs.
- **A learned value model encodes whatever priorities its training data
  encodes.** Trained on a real mission's history it would reproduce that
  mission's historical weighting between instruments and between science and
  operational products, including any weighting nobody intended. There is no
  mechanism in this package to audit that, and the synthetic generator does not
  exercise the problem.
- **The uncertainty output is a dispersion measure, not a probability.** Using
  it as a calibrated interval would overstate confidence by the amounts in the
  coverage table above.
- **Out-of-distribution inputs are not detected.** The models will return a
  confident-looking number for an instrument class, a size or an age the
  generator never produced.
