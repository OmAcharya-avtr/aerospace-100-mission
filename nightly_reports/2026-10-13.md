## What each defect was

### P001 BeamTwin — a pickled model is bound to the version that wrote it

`models/surrogate.joblib` records `sklearn_version: 1.8.0`. scikit-learn 1.9
removed the private module the ensemble's loss object is pickled against, so
`joblib` raises `ModuleNotFoundError: No module named '_loss'`. The four errors
are all in `tests/test_surrogate.py::TestCommittedModel`; the other 247 pass
because everything that is not the committed artifact is closed-form physics.
**This was not a cold-clone artifact** — the working tree failed identically, so
it had been true for as long as the container has had 1.9.

The dependency was a bare `scikit-learn`, no bound of any kind. Now
`>=1.8,<1.9`, which is the range the artifact actually loads under, confirmed by
execution. The real fix — export the trees to a version-neutral `.npz` and drop
the pickle — is named in limitation 16 and **was not done**. Retraining under
1.9 was rejected for the same reason the `margin_histogram.png` finding was
rejected on 2026-10-12: it pins the artifact to today's upstream and moves the
identical break to the next release.

### P004, P023, P032 — one upstream rewrite, three different correct answers

PuLP 4.0 is a rewrite on a Rust core. It removed `LpVariable(name, cat=…)`,
`pulp.PULP_CBC_CMD`, `pulp.LpStatus` and `LpProblem.status`. PuLP 3 added
snake_case aliases that 2.x does not have. The three products were each written
against a different generation, and an unbounded floor hid it.

| PuLP | P004 | P023 | P032 |
|---|---|---|---|
| 2.9.0 | 106 pass | 1 fail (`add_variable`) | **25 fail** |
| 3.3.2 | 106 pass | 185 pass | 387 pass |
| 4.0.0 | **17 fail** (`cat=`) | **1 fail** (`PULP_CBC_CMD`) | 387 pass |

**The first answer this session reached was wrong, and measurement caught it.**
Commit `9eea674` bounded P004 to `<3` by reasoning from its README, which
described PuLP 2.x deprecation warnings. Running the suites showed P004's
numbers were produced under 3.x, that P023 works on 3.x *only*, and that P032 —
which the same instinct would have bounded to `<3` — **loses 25 tests on 2.9.0**
because it was written against 4.0.0. The `<3` bound on P032 was reverted before
it was ever committed. `2f83ec3` corrects all three from measurement.

P032 also carries a latent defect **no test reaches**: `flow.py:356` reads
`pulp.LpStatus[problem.status]` and 4.0.0 has neither name. `solve_with_pulp`
raises `NoSolverError` before that line whenever no MILP solver is installed,
which is the case here and is why its README says no `pulp` solve was ever
performed — so its 387 passing tests say nothing about that line. A user who
installs CBC, HiGHS or GLPK and asks for `backend="pulp"` gets `AttributeError`.
Established by attribute probe, **not** by execution, and deliberately **not
patched**: there is no solver here to execute a patch against, and an
unexecutable change to a published product is worse than a recorded limitation.

### P025 FDIScope — the suite passes and the numbers still move

Found by accident. `validation/detection_benchmark.py` was executed to verify an
unrelated claim about exit codes, and its output file came back different from
the committed one. Under scikit-learn 1.9.1 the `learned` detector's false-alarm
rate moved 0.1500 → 0.1444, its alarm count 220/306000 → 208/306000, a detection
figure 0.7921 → 0.8504, and six of nine delay rows shifted. **The committed
0.1500 is quoted in the product's own limitation 3.** Re-run under 1.8.0 the
committed file reproduces exactly — the only differing lines are `campaign build`
and `wall time`.

So the fit is seeded and reproducible *at a fixed version*: `random_state` fixes
the stream, not the algorithm. **No verdict changed in either direction** — V3-C1
is FAIL under both and the closed-form methods are bit-identical. This is the
form of the defect that would never have surfaced as a test failure, and it is
the reason the other 36 unbounded products are recorded as exposure below.

## The P053 escalation, with new measured evidence

P053 remains the single blocker for nine finished, gate-PASS products. It is an
owner decision and this session did not make it. **Seventh escalation.**

What is new is that the precedent the 2026-10-12 session cited has now been
**verified by execution, and it is stronger than that session described.**

- `products/P025/validation/detection_benchmark.py` was run tonight. It prints
  `C1: FAIL` and `V3 summary: C1 FAIL, C2 PASS, C3 measurements above`, and its
  **process exit status is 0**. P025 is published and gate-passing.
- The mechanism is not a considered convention. P025's four validation scripts
  contain **no exit-code logic at all** — no `return 1`, no `sys.exit`, nothing —
  so they exit 0 because Python exits 0 when a script finishes.
- **P039 is the stronger case.** `validation/validate_interval_coverage.py` has
  `def main() -> int:` and an **unconditional `return 0` at line 243**, while its
  committed output carries **48 `FAIL` rows**, including coverage of 0.267
  against a 0.50 nominal at −6.46σ and 0.080 against 0.50 at −18.96σ. It is
  published and the gate passes it.
- Repository-wide: **150 of 369 validation scripts** encode a verdict in their
  exit status; the other 219 do not. **Ten of the fifty published products carry
  `FAIL` tokens in committed validation output.**

So gate check 6 does not measure whether a product's validations pass. It
measures whether a script's author chose to put the verdict in `$?`. P053's
negatives — bias −8.6 % at T=200 and +13.5 % at T=1000 against a declared 8.8 %
tolerance — are **milder than P039's, which are published.** P053 is being held
for a stylistic choice its siblings did not make.

That argument is for the owner to accept or reject. **The gate was not edited, no
threshold was loosened, no check was skipped, no passing subset was gated, no
product was set to `APPROVED`, no row was written to `APPROVAL_LOG.md`, and
nothing was attributed to the owner.** The 2026-10-02 precedent stands: a session
that changed P035's `return 1` to `return 0` was refused by a safety classifier
