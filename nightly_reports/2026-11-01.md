### P084 TransferGap — gate verdict BLOCKED, exact output

```
P084  BLOCKED    188 tests
         ! validation/probe_working_directories.py exit 1: no output
         ! validation/validate_cli.py exit 1: no output

repository  PASS

Total tests passing: 188
VERDICT: PUSH BLOCKED
Blocked products: P084
Set each to NEEDS HARDENING in products.yaml and do not publish it.
```

P084 is set to **`NEEDS HARDENING`** in `products.yaml` and **nothing from it was
published.** No check was skipped, no threshold was loosened, the gate was not
edited, and the parts that passed were not pushed to a product repository. The
monorepo commit `a88d36e` carries the built source at `NEEDS HARDENING` status
so the work is not lost a third time; that is not publication.

**Root cause, diagnosed rather than guessed.** The gate runs each validation
script as `python3 <name>` with `cwd=validation/`, `PYTHONPATH=<product>/src`
and `MPLBACKEND=Agg` (`release_gate.py:165`). Reproducing that invocation
exactly:

1. The two failures are **one** root cause. `probe_working_directories.py`
   reports `non-zero exit statuses : 4 of 36`, and all four are
   `validate_cli.py` run from the four probed directories. The probe is
   correctly reporting the other script's failure.
2. `validate_cli.py` fails 2 of its 11 checks: *no cache or config directory
   exists anywhere in the tree* and *no compiled bytecode file exists anywhere
   in the tree*.
3. The build agent's own hand-back predicted this would be caused by the gate
   running pytest before the cache check. **That hypothesis is wrong**, and it
   was tested rather than accepted: the tree was emptied of every cache
   directory and `.pyc` file and the script re-run, and it **still exits 1**,
   reporting 11 bytecode files.
4. The script writes them **itself**. Its own interpreter imports `transfergap`
   and `_bootstrap` without `PYTHONDONTWRITEBYTECODE=1`, creating
   `src/transfergap/__pycache__/*.pyc` and
   `validation/__pycache__/_bootstrap.cpython-313.pyc`, and then scans the tree
   for exactly those files. The agent set that variable on every subprocess it
   spawns and not on the process doing the scanning.

This is a **fourth occurrence of the self-reporting-scanner class** already
recorded in `PRODUCT_BUILD_GUIDE.md`, which notes that "three consecutive
sessions introduced this defect in the act of writing about it." The guide's
existing text tells a scanner to delete its own previous output before scanning;
P084 did that for the absolute-path scan and still reported its own bytecode.
The guide needs the general rule: **a tree scanner must set
`PYTHONDONTWRITEBYTECODE=1` on its own interpreter, not only on its children,
or exclude artifacts created after its own start time.**

None of the polluting files is tracked — `__pycache__/` is gitignored and the
committed tree is clean. The fix is small and belongs to a session that can
re-run the script and the gate afterwards. **The product's method is not
implicated:** 188 tests, 93 validation checks and 19 negative controls all pass,
ruff is clean under both installations, every dependency is bounded on both
sides, and the specification's stated expectation was confirmed — the learned
conditional quantile under-covers at all four field sample sizes (0.8761, 0.8754,
0.8769, 0.8843 against a declared 0.95) while being the tightest limit at every
one of them, which is a baseline win and was kept as measured.
