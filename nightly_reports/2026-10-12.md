## What was fixed

### 1. P058 one-ulp boundary defect — patch applied, executed, gate-verified

The previous session derived the root cause and wrote a complete patch but
deliberately did not apply it, having no environment that could run a single
test. That judgement was right and the patch was correct. It is now applied.

The test `test_cusum_is_invariant_under_an_affine_rescaling_of_the_channel`
asserted bit-exact equality across a floating-point pipeline *and* across the
strict boolean comparison that follows it. The invariance is exact in exact
arithmetic and is **not** exact in binary floating point: `(a + s·x − a)/s` need
not round-trip to `x`. With `mu0 = 3.0`, `sigma0 = 0.1`, `x = 1.0`, `k = 0.5`
the two arms are `0.5` and `0.5000000000000009`, a gap of `8.881784197001252e-16`,
and `h = 0.5` falls between them — so the strict comparison yields `False` on the
plain chart and `True` on the rescaled one.

- Statistics are now compared with `math.isclose(rel_tol=1e-9, abs_tol=1e-12)`.
- The booleans must still agree **except** at the decision boundary, and that
  exception is bounded: it is allowed only when the statistic sits within `1e-9`
  of `h`.
- A named regression test pins the literal counterexample, because
  `.hypothesis/` is gitignored and a fresh clone otherwise loses the cached
  example and rediscovers this corner only by chance.
- **The detector was not changed.** `CUSUM.update` is correct and its `h` values
  are calibrated against measured ARL0; toleranceing the comparison inside
  `update()` would silently move every operating point in the package. The
  `CUSUM` docstring carried no exactness claim to withdraw, so the measured
  caveat was documented there instead.

### 3. P001 `margin_histogram.png` — investigation closed, root cause identified

Opened 2026-10-10 as "unexplained and uninvestigated", in a **published**
product. Full analysis in
[`tracking/FINDING_P001_PNG_RENDERER_DEPENDENCE.md`](../tracking/FINDING_P001_PNG_RENDERER_DEPENDENCE.md).

Re-running `examples/margin_histogram.py` reproduced the byte sizes **exactly**:
66,047 → 75,602. The committed file was copied aside first and restored after,
so the tree stayed clean.

**Cause: the PNG records its own renderer.** The committed file's `tEXt` chunk
says `Matplotlib version3.10.9`; this container ships `3.11.2`.

The previous session was right to reject the metadata explanation. Measured over
the decoded images (identical `IHDR` 1092×672 RGBA, identical `pHYs`):

- 84,846 of 733,824 pixels differ — **11.56 %**.
- Deltas are **saturated, not subtle**: max channel delta 255, median 95 over
  differing pixels, 4.77 % of the image differing by more than 128.
  Anti-aliasing cannot do that.
- Ink quantity is nearly unchanged — 59,134 → 58,591 non-white pixels — but
  **ink IoU is 0.257**, and an exhaustive search over all shifts within ±12 px
  raises it only to 0.332. Not a translation.

**Mechanism:** the figure draws two `histtype="step"` histograms with 220 bins at
1.2 pt across ~1000 px of axes — about 4.5 px per bin, i.e. a long thin zigzag
polyline, the structure most sensitive to how Agg snaps and rasterizes thin
paths. Displacing a 1.2 px line sub-pixel yields a saturated delta along its
whole length. Less pixel-aligned rasterization also compresses worse, which is
why the second `IDAT` grows 351 → 9,906 bytes.

**The data did not change, and that is the part that matters.** The script is
fully seeded (`N_MC = 300_000`, `SEED = 5`). The rerun printed
`P_fade=9.2667e-04, mean=+10.12 dB, p01=+2.59, p50=+10.13`; the README states
`9.27e-04 at n = 300,000, seed 5`. Exact agreement. **P001's published numbers
stand and P001 needs no correction.**

Deliberately **not** "fixed" by regenerating: that would pin the artifact to
matplotlib 3.11.2, move the identical problem to the next upgrade, and churn a
published product for no scientific gain.

### 4. Gate-induced artifact drift — fully characterised, and it is not scientific

`MISSION_STATUS.md` has carried an open question about whether committed outputs
reproduce. This session answers it by measurement rather than by inference.

The full gate run left **28 tracked files modified** — P051 ×1, P052 ×3,
P054 ×9, P055 ×2, P056 ×1, P058 ×12 — comparable to the 23 seen on 2026-10-10.
All 131 paired changed lines were compared **token by token**. Every single one
falls into exactly three buckets:

| Cause | Evidence |
|---|---|
| **Wall-clock and derived timing** | µs/ms/s per sample, throughput, and speed ratios. Example: an entire row of `P054/validation/validate_surrogate.txt` is byte-identical — mean `3.718990`, error `−2.607e-06`, CI `3.71791`/`3.72007`, final `6.454e-05` — except one column, `0.05 → 0.06`, which is seconds. |
| **Kernel string** | `platform.platform()` → `Linux-6.18.44-fc-v80-…` vs `-fc-v114-…`. **All nine P054 files are this one cause**, confirming the 2026-10-10 diagnosis exactly. |
| **Dependency version** | `hypothesis 6.168.5 → 6.169.0`, from this container's fresh install (P056, P058). |

**No measured scientific quantity moved anywhere.** Means, errors, confidence
bounds, counts, probabilities and every PASS/FAIL verdict are identical. Where a
`PASS` line quotes a ratio the ratio moves — `[25.3x] → [22.6x]` — because the
ratio is of two timings; the verdict stays `PASS`.

One change was **correct and wanted**: `P058/validation/outputs/validate_cli.txt`
moved `302 passed` → `303 passed`.

**Conclusion, stated no more strongly than measured:** bit-for-bit
reproducibility of committed *outputs* is unachievable in the current format
because those outputs deliberately record their environment. **Numerical
reproducibility is achieved.** The 2026-10-11 narrowing was correct and is
reinforced, not reversed. Reproducibility should be asserted over numbers, which
are stable, never over bytes, which are not.

Accordingly the drift was **split, not blanket-committed and not blanket-reverted**:
P058's twelve regenerated outputs are committed, because P058's suite genuinely
changed and its outputs must reflect that; the seventeen files in P051, P052,
P054, P055 and P056 were reverted, because nothing about those products changed
and committing kernel strings and wall-clock noise is churn in a published tree.

### The gate's "no output" message is misleading, and the owner should see why

The gate reports `validation/validate_thresholds.py exit 1: no output`. That
reads like a script that crashed silently. It did not. `check_scripts` reports
the last line of **stderr**:

```python
last = (out.stderr or "").strip().splitlines()
r.fail(f"{sub}/{script.name} exit {out.returncode}: "
       f"{last[-1][:120] if last else 'no output'}")
```

P053's script writes its entire diagnosis to **stdout** and nothing to stderr,
so `last` is empty and the gate prints `no output`. The script in fact prints
its `FINDING` lines verbatim and a `SUMMARY  n/m checks PASS` line, then returns
`0 if all(results) else 1`. **The gate's own output therefore presents the
mission's most carefully reported honest negative as a silent crash.** This is a
diagnostic defect, not a verdict defect — it changes nothing about pass or fail.
It was **not fixed here**, because any edit to the publication authority in an
unattended session is out of bounds, and it belongs with the P053 decision below
since it lives in the same function.

`products/P053/validation/validate_thresholds.py` exits **1 by design**. It
publishes two genuinely failing variance-CUSUM threshold-transfer checks — bias
**−8.6 % at T=200** and **+13.5 % at T=1000** against a declared **8.8 %**
tolerance — rather than widening the tolerance until they pass. That is ADR-011's
honest-negative policy working exactly as written. Gate check 6 requires every
`validation/*.py` to exit 0, so the gate reads an honest measurement as a broken
script and blocks the batch.

**New evidence this session, which reframes the decision.** This is not a novel
dilemma and the repository already contains a settled convention:

- **P025 carries two reported-FAILED checks and passes the gate**, because they
  print `FAILED` and **exit 0**.
- The identical conflict arose with **P035 on 2026-10-02** and is recorded in
  project memory as an explicit owner decision.
- On 2026-10-02 a session tried changing P035's `return 1` to `return 0` and
  **the safety classifier refused it as a CI bypass** — correctly, since from
  outside it is indistinguishable from editing a check to pass. The standing
  instruction from that session is *do not retry this unattended*, and it was
  not retried tonight.

So the honest framing is that **P053 and P035 deviate from the repository's own
existing convention, which P025 established.** Option (A) is therefore
"bring P053 into line with P025", not "loosen a check".

The decision is narrow:

- **(A)** The gate honours a declared `expected_exit` or `honest_negative: true`
  marker — or, equivalently and more cheaply, P053's script adopts the P025
  convention: print every `FAILED` line and the numbers verbatim, exit 0.
- **(B)** ADR-011 negatives report through a mechanism that exits 0 while
  keeping the `FAILED` lines verbatim.

The argument worth putting, in the gate's own words: its header states the rule
it enforces is *"the product actually works", not "the test command exited 0"*,
and check 6 currently conflates **did the validation run** with **did every
measured quantity land inside tolerance**. Either option separates those two and
**neither hides anything**. Recommend bundling the `no output` stderr/stdout
reporting fix into the same change.

**Not decided here, and no approval invented.** Nothing was set to `APPROVED`, no
row was written to `APPROVAL_LOG.md`, and no words are attributed to the owner.
