## The gate blocked first, and why that matters

`release_gate.py` over all ten products returned **`VERDICT: PUSH BLOCKED`** on
its first run at 3,873 tests passing, with three distinct failures. All three
were real. Each was fixed at its source in commit `3e0c671`; no check was
skipped, no threshold loosened, the gate itself was not touched, and nothing
was published from the blocked run.

**1. P077 and P079 failed ruff with UP042** — "Class X inherits from both `str`
and `enum.Enum`". The cause is a version skew the mission had carried as an
open note without connecting it to the gate: the build agents measured ruff
clean under the pinned venv's **ruff 0.14.2**, while the gate runs the system
ruff, which is **0.16.9** and enforces UP042. **A product can be ruff clean at
build time and blocked at gate time with no change to its source.** Fixed by
inheriting from `enum.StrEnum`, which requires Python 3.11 and is therefore
inside both products' declared `requires-python`.

The fix was verified behaviour-neutral rather than assumed. Neither enum is
ever formatted with `str()` or an f-string anywhere in either product — every
use is an identity comparison, a type annotation or `.value`. Re-running both
full suites after the change gave 777/0/0/0 and 335/0/0/0, unchanged, with
attributes agreeing with literal counts, and both products are now clean under
**both** ruff versions. Re-running every validation and example script produced
outputs in which **no numerical value changed**; the only differences were
environment-header tool versions, because that re-run used the system
interpreter.

**2. Repository check 8 failed: absolute private path tracked**, at
`nightly_reports/2026-10-21.md:23`. Four consecutive nightly reports and this
session's checkpoint had written the owner's absolute Mac folder path into
tracked files — while documenting the folder-grant defect. Normalised to a
leading `~` in all five files, which keeps the folder identifiable and the
record intact.

**This blocker was latent for four nights.** It was introduced on 2026-10-21
and no gate ran on 2026-10-21, 10-22, 10-23 or 10-24, so nothing detected it. A
gate that is not run does not fail; it simply stops telling you anything. The
cost of the three nights that produced only a report was not just those nights.

**3. This session introduced the same defect in the act of writing about it** —
the third consecutive session to do so. The 2026-10-25 report and checkpoint
both named the container's pinned-venv path under `/home`. Also normalised. The
working tree now has zero matches for the gate's own path pattern.

The second gate run returned **`VERDICT: PUSH ALLOWED`**. From

## Carry-over closed by measurement: the PuLP question

The open question — do published P004, P023 and P032 still pass with no PuLP
solver present — is now answered, and the premise turned out to be wrong.

**`pulp` 3.3.2 DOES ship an available bundled solver**:
`listSolvers(onlyAvailable=True)` returns `['PULP_CBC_CMD']`. The solver only
disappears at pulp 4: at **4.1.0** and **4.2.0** that call returns `[]` and
`PULP_CBC_CMD` is not in `listSolvers()` at all.

Measured, each by running the product's own suite:

| Product | Declared pin | Resolves to | Result |
|---|---|---|---|
| P004 PassPlanner | `pulp>=2.7,<4` | 3.3.2 | **106/106 PASS** (+218 `PULP_CBC_CMD` deprecation warnings) |
| P023 AllocLab | `pulp>=3,<4` | 3.3.2 | **185/185 PASS** |
| P032 ConstelLink | `pulp>=3` (no ceiling) | 4.2.0 | **387/387 PASS** |

Under the container's system pulp **4.2.0**, which is outside P004's and P023's
declared range:

- **P004: 17 of 106 FAIL** — `TypeError: LpVariable.__init__() got an
  unexpected keyword argument 'cat'`.
- **P023: 1 of 185 FAIL** — `AttributeError` on `pulp.PULP_CBC_CMD`.
- **P032: 387/387 PASS** — it calls `pulp_solver_available()`, sees the empty
  solver list, and falls back to scipy. It already documents "pulp 4.0.0 ships
  no bundled solver".

**Conclusion: no published product is broken as declared.** The failures are
pulp 4 **API breaks**, not solver absence, and P004 and P023 are protected
precisely by the `<4` ceiling that the mission's own bounded-on-both-sides rule
required. Two consequences for the owner:

1. **P032's `pulp>=3` is unbounded above** and violates that same rule. It
   resolves to 4.2.0, outside the API it was written against, and passes only
   because of runtime detection. The declaration should be bounded.
2. **P004 and P023 are on a deprecation countdown.** Their code uses an API
   that pulp 3.3.2 warns about 218 times and pulp 4 removed. They work today
   only because of the ceiling.

gradient-boosted model on calibration (ECE 0.012237 against 0.027302) and is
published as the forecast while the learned score is published as a ranking.
The demand-over-supply ratio the specification **named** as the baseline turned
out to be the weakest of three candidates (AUC 0.6010 and 0.6228 against 0.9230
for a per-request ratio, and below 0.5 on a smaller split); the strongest was
made the baseline, which **cut** the learned margin by about 0.36 AUC rather
than inflating it. Priority-ordered first-fit ties the proven optimum on 75 of
160 instances. The predicted fairness price is **0.000000** on all 16 feasible
instances — a null result, published beside two constructed counterexamples
rather than replaced by them. 144 of 160 instances are infeasible under their
own declared floors.

**P074 OrbitDrift.** The analytic form **wins the headline task.** At nominal
0.90 coverage on the extrapolation task, the only calibrated interval is
analytic (0.8991, CI [0.8804, 0.9159]); the only predictor that does not
under-cover is analytic (0.9474); **no learned predictor reaches 0.90**, the
best being 0.8750. The analytic form also wins point prediction, 0.1299 median
absolute log error against 0.1391. A learned model denied the object's own
curve is 3.91× worse, so the information is in the curve, not in the learning.
The learned model wins point prediction on the cold task only (0.5942 against
0.7410), where **every** predictor under-covers, so that task has no
operationally usable result. The 1 km/day rule of thumb covers 0.3017. The
measured growth exponent is 0.9685 ± 0.0628 above 1100 km perigee — linear in
time, as a constant mean-motion error predicts — against 1.2683 ± 0.3914 below
450 km. The specification predicted an analytic form would match at most
altitudes; it does.
