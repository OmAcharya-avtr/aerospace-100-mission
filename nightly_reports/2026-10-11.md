### 5. P058 one-ulp defect — root cause independently reproduced, patch ready, NOT APPLIED

The arithmetic was re-derived tonight in plain Python on the Mac, independently of
the previous session report:

| Quantity | Value |
|---|---|
| `y = 3.0 + 0.1*1.0` | `3.1` |
| `z_plain` | `1.0` |
| `z_scaled = (3.1 - 3.0) / 0.1` | `1.0000000000000009` |
| `S_plus_plain = max(0, 1.0 - 0.5)` | `0.5` |
| `S_plus_scaled` | `0.5000000000000009` |
| gap | `8.881784197001252e-16` |
| `S_plus > h` with `h = 0.5` | plain `False`, rescaled `True` |

Every figure matches the outgoing checkpoint. This confirms the diagnosis is
arithmetic and not a defect in the product mathematics: the invariance holds in exact
arithmetic, and the test asserted something binary floating point cannot deliver.
Note this reproduces the arithmetic, **not** the product code path —
`telemdrift.detectors` imports numpy, which the Mac does not have.

**The patch is not applied.** A test-file edit that cannot be executed is a change to
the one thing the gate reads, made blind. Since the batch cannot publish until P053
is settled and the next session must re-gate regardless, the patch costs nothing by
waiting and risks nothing. It is recorded here in full so it can be pasted in and
gated in minutes.

Replace `test_cusum_is_invariant_under_an_affine_rescaling_of_the_channel` in
`products/P058/tests/test_properties.py` with:

```python
@given(SAMPLES, st.floats(min_value=0.5, max_value=20.0),
       st.floats(min_value=0.1, max_value=10.0))
@settings(max_examples=150, deadline=None)
def test_cusum_is_invariant_under_an_affine_rescaling_of_the_channel(xs, h, scale):
    '''CUSUM standardises by mu0 and sigma0, so feeding a + s*x with mu0 = a and
    sigma0 = s reproduces the plain chart to within floating-point rounding. This
    is the property that lets a threshold calibrated on one channel transfer to
    another.

    The identity is exact in exact arithmetic and is NOT exact in binary floating
    point: (a + s*x - a) / s need not round-trip to x. The error is a few ulp in
    the statistic, but the alarm is max(S_plus, S_minus) > h, a strict
    comparison, so a few ulp can flip the boolean when the statistic lands on h.
    The statistics are therefore compared with a tolerance, and the booleans are
    required to agree except at that boundary, which is pinned explicitly in
    test_cusum_rescaling_disagrees_by_one_ulp_at_the_decision_boundary.
    '''
    shift = 3.0
    tol = 1e-9
    plain, scaled = CUSUM(h=h), CUSUM(h=h, mu0=shift, sigma0=scale)
    for x in xs:
        fa = plain.update(x)
        fb = scaled.update(shift + scale * x)
        assert math.isclose(plain.s_plus, scaled.s_plus, rel_tol=1e-9, abs_tol=1e-12)
        assert math.isclose(plain.s_minus, scaled.s_minus, rel_tol=1e-9, abs_tol=1e-12)
        if fa != fb:
            assert abs(max(plain.s_plus, plain.s_minus) - h) <= tol
            assert abs(max(scaled.s_plus, scaled.s_minus) - h) <= tol


def test_cusum_rescaling_disagrees_by_one_ulp_at_the_decision_boundary():
    '''Regression test for the example the 2026-10-10 release gate found.

    .hypothesis/ is gitignored, so a fresh clone loses the cached counterexample
    and this corner is rediscovered only by chance. The literal inputs are pinned.

    With shift=3.0, scale=0.1, x=1.0: y = 3.1, z_plain = 1.0 exactly, while
    z_scaled = (3.1 - 3.0) / 0.1 = 1.0000000000000009. With k = 0.5 the arms are
    0.5 and 0.5000000000000009, a gap of 8.881784197001252e-16, and h = 0.5 falls
    between them, so the strict comparison gives False on the plain chart and
    True on the rescaled one. Arithmetic re-derived 2026-10-11.
    '''
    shift, scale, h, x = 3.0, 0.1, 0.5, 1.0
    plain, scaled = CUSUM(h=h), CUSUM(h=h, mu0=shift, sigma0=scale)
    fa = plain.update(x)
    fb = scaled.update(shift + scale * x)
    assert plain.s_plus == 0.5
    assert scaled.s_plus > plain.s_plus
    assert scaled.s_plus - plain.s_plus < 1e-14
    assert fa is False
    assert fb is True
```

The docstring of `CUSUM` in `src/telemdrift/detectors.py` should also lose any
claim that the transfer is exact; the honest statement is that it is exact in exact
arithmetic and agrees to within rounding, which can flip a single alarm decision
when the statistic lands on `h` to within an ulp. **The detector itself must not be
changed.** Its mathematics is correct and its `h` values are calibrated against
measured ARL0; toleranceing the comparison inside `update()` would silently move
every operating point in the product.

enforce is *the product actually works*, not *the test command exited 0*. Check 6
currently conflates two different questions — did the validation run, and did every
measured quantity land inside its declared tolerance. Both options above separate
them. Neither hides anything.
