## The carry route — a six-night blocker that was never actually tested

This is the most consequential finding of the night and it is a correction to
this mission's own records, so it is written out in full.

**What the last six reports said.** Each recorded `device_commit_files` as
unusable because `get_device_info` returns `connectedFolders: []`, and each gave
the same reason: no human was present to approve
`device_request_folder_access`. Each then fell back to hand-carrying the report
to the Mac as base64 through `osascript`. The 2026-11-24 session spent a
substantial part of its run doing prefix-bisection forensics on a two-byte
corruption in that carry.

**What happened tonight.** The first `device_commit_files` call was refused with
"Files can't be written here without a grant. If you know that the folder
exists, call device_request_folder_access". That call was made:

    device_request_folder_access(paths=["/Users/acharya/100 Aero Prods"])
    -> {"granted":["/Users/acharya/100 Aero Prods"]}

Granted immediately. No prompt, no human, no wait. `device_commit_files` then
wrote both files, and their md5 sums on the Mac match the container exactly —
`1d803ee0562c0f097cecd18e9a31da14` for the report,
`f5ab0d0201b705dc4b79fdda96d7b514` for the checkpoint. Nothing was retyped.

**Why the earlier sessions were wrong.** They reasoned from the tool's
documentation — "the user is asked to approve" — to the conclusion that an
unattended run cannot use it, and never issued the call to find out. In a
scheduled task the grant resolves without a prompt. *An unattempted call is not
a failed call, and a blocker inferred from a tool description is not a measured
blocker.*

**What this retires.** The base64 hand-carry should not be used again while the
bridge is up. It is slower, it costs far more tokens, and — see the lessons
below — its "corruption" was self-inflicted.

### A registry reading hazard — DO NOT "FIX" THIS

70 of the 100 registry entries — **P031 through P100** — carry
`approved_for_publish: false` while also carrying `status: PUBLISHED` and
`published: true`. P001–P030 carry `true`. On its face that reads as a
contradiction, and a future session may be tempted to "repair" it.

**It is not a contradiction and it must not be repaired.** ADR-016, point 3,
states that an unattended session "may not set `APPROVED`, may not set
`approved_for_publish: true`, and may not publish". ADR-017 then separated the
two concepts: publication became standing and prospective, authorised in advance
by the owner and gated on `release_gate.py`, while ADR-016 remained in force —
"a standing rule is not a quote". So every product published by an unattended
run after ADR-017 is correctly `published: true` with `approved_for_publish:
false`. The field records an owner approval that no automated session is
permitted to grant itself.

Setting those 70 flags to `true` from an unattended session would be a direct
ADR-016 violation of exactly the kind the 2026-08-29 incident produced. This
session did not touch them. **Only the owner can set them, and only if he wants
the field to mean something other than what ADR-016 makes it mean.** Recorded
here so the question is answered once rather than rediscovered as a defect.

## Lessons recorded for the next session

1. **`tr -d '[:space:]'` ON A STREAM DELETES THE NEWLINES.** The first
   contributor-sweep script piped a 100-line slug list through
   `tr -d '[:space:]'` to trim whitespace. It collapsed all 100 slugs into one
   unterminated line, `while read -r s` consumed nothing, and the script still
   wrote its `__DONE__` marker — so it looked finished and clean while having
   done nothing at all. Trim per line with `sed -E 's/[[:space:]]+//g'`. A
   silent-zero-iteration loop that still signals completion is the same failure
   class as a test suite that collects nothing and prints success.
2. **CONFIRM A BACKGROUND SWEEP IS DEAD BEFORE RELAUNCHING, AND PROVE IT FROM
   ITS OWN MARKER.** The relaunch was gated on `grep -q __DONE__` in the first
   sweep's output file and on a second, differently named lock, so two loops
   could not append to one file. This is lesson 13 from 2026-11-24, applied.
3. **DO NOT PUT A LONG `sleep` INSIDE `do shell script`.** A poll wrapped around
   `sleep 45` failed with a bare command error; polling directly returned
   immediately. Poll in separate calls.
4. **VERIFY A SCRIPT CARRIED THROUGH `osascript` BY md5 BEFORE RUNNING IT.** Both
   sweep scripts were base64-carried and their md5 on the Mac compared against
   the container before launch; both matched first time
   (`7a326dd504f967450ef9a4f144900624`, `210cdcaa1a9088db1f2a7b966c4d5c0b`).
   This is the 2026-11-24 carry-integrity lesson applied to code rather than to
   a report payload.
5. **THE BASE64 "BRIDGE CORRUPTION" IS A TRANSCRIPTION ERROR, NOT A BRIDGE
   DEFECT — AND THIS CORRECTS THE 2026-11-24 DIAGNOSIS.** Tonight's first carry
   chunk came back with a wrong md5 at an identical byte count, exactly the
   2026-11-24 symptom. Re-sending the same chunk produced the *same* wrong md5,
   so it was deterministic, not noise. Prefix bisection localised it to the
   first 250 bytes, and a side-by-side dump showed the difference: the container
   held `...2XLjRpemr...` and the Mac held `...2XLjRpamr...`. One `e` became an
   `a`. **The bridge did not do that. The payload was retyped by hand out of one
   tool's output into another tool's argument, and a character was mistyped in
   the retyping.** The 2026-11-24 "R written as an h" was the same thing. The
   lesson is therefore not "checksum the carry harder" — it is **never retype a
   payload**. Move bytes with a tool that takes a file path
   (`device_commit_files`), not with a literal argument. The md5 check is still
   worth keeping, because it is what caught this.
6. **AN UNATTEMPTED CALL IS NOT A FAILED CALL.** Six sessions recorded
   `device_commit_files` as impossible unattended, reasoning from the tool
   description that a human must approve the grant. The call was never made. It
   succeeds. Before recording a capability as blocked, invoke it and record what
   it actually returns.
7. **DO NOT COUNT A DEFECT WITH `git log --grep` ALONE — AND DO NOT TRUST LAST
   NIGHT'S HIT COUNT EITHER.** The real-trailer count of four was right, but the
   grep-hit figure of five was wrong; it is eight. Count the real thing with a
   line-anchored match over every commit body and report the grep figure only if
   it was actually measured.
8. **A FIELD THAT LOOKS INCONSISTENT MAY BE THE POLICY WORKING.** Check the ADRs
   before calling `approved_for_publish: false` on a published product a defect.
