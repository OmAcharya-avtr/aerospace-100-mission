## The path that is still broken: bulk file transfer into the Mac

The three Phase −1 checks verify the *last* leg of publication (Mac → GitHub).
They do not verify the *first* leg (container → Mac), and that leg is down.

- `mcp__remote-devices__device_commit_files` was called with the real bundle
  (`27dbe63..main`, 1,956,390 bytes, already delivered to the conversation as
  `file_uuid eeda0345-2608-4d88-8408-faff6d946cfb`) and refused:

  > Files can't be written here without a grant — call
  > `device_request_folder_access` with the folder path (the user is asked to
  > approve). The `device_*` tools honor only this session's connected folders.

- `get_device_info` reports **`connectedFolders: []`** — no folder is connected
  to this run, although the task is configured with
  `/Users/acharya/100 Aero Prods` and the scheduler's own notice for this run
  claims that folder is connected. The notice and the device disagree; the
  device is correct.
- `device_request_folder_access` raises a prompt that a human must answer. No
  human is present in a 03:07 UTC automated run, so it was not called: it would
  have blocked the run rather than fixing it.
- The `Control your Mac` osascript bridge is a *separate* grant and is working.
  That is how this report and the fix below reached GitHub. It carries shell
  commands, so it can write text files the session composes, but it cannot
  carry a 1.9 MB git bundle or any binary: the only transport is base64 inline
  in the script, which for this bundle is 107 chunks of 60 KB — far beyond what
  one run can spend.

**Consequence, stated plainly: tonight a batch could have been built and could
not have been published.** Source trees are text and would have survived the
osascript route; the screenshots the README standard requires, and any bundle,
would not. That is the v4 failure mode in new clothing — build, report success,
publish nothing — so **no build was started.** This is the branch Phase −1
exists to force, and taking it is the correct outcome, not a failure of the run.

introduced with P026 WahbaKit in Batch 03 and has been broken since.

by `yaml.safe_load` in the container and by re-running `quota_report.py`, which
now produces output again. This is published in the same commit as this report.

Composition is 2 flagship, 3 medium, 5 compact with 7 of 10 AI-enabled, as
required. Levels are 2 x L1, 5 x L2, 3 x L3, chosen against the measured gap:
L1 has only four slots left in the whole mission, so this batch takes two and
later batches must stop producing L1 products.

All ten names were checked on PyPI this session by
`GET https://pypi.org/pypi/<name>/json` and returned HTTP 404 — free:
`hilforge`, `constellink`, `edgeinfer`, `faultinject`, `telemetryool`,
`rtclock`, `framesync`, `dopplerkit`, `latencynet`, `bitflipsim`.
Twenty-eight packages named in the spec's alternatives guidance were checked
the same way and confirmed to **exist**, so no build agent has to guess whether
a competitor is real.

**One product was dropped during specification, which is the part worth
reporting.** The obvious compact product for the satellite-communications slot
was a CCSDS packet and framing library, `ccsdskit`. The name is free. It was
dropped because `ccsdspy` and `spacepackets` already do that job well, so it
had no honest answer to the ADR-018 question. Its slot went to `framesync`,
whose claim is narrower and real: frame-level link performance — sync
acquisition statistics and frame-loss rate versus Eb/N0 — which is the gap
between a codec library and a link budget, and which no package provides.

**Level 4 entry plan.** P031 and P033 carry the groundwork: hardware
abstraction layer with simulation/device parity, simulation mode, dry-run mode,
deployment and recovery procedures as executable checks, and the benchmark
harness. The labelling rule is written into the spec as absolute — those
products are `Level 3, hardware-pending`, never Level 4, until measured timing
and resource use come from the Jetson Orin Nano itself. No Level 4 number may
come from a simulated backend, an extrapolation or a datasheet. That means L4
stays at 0 after Batch 04 and the owner will have to run the benchmark harness
on the board at some point for it to move at all.
