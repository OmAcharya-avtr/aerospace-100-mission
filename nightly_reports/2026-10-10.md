## The gate found a real defect that four separate measurements had missed

**P058 is newly blocked, and it is not the carried-forward P053 problem.** The
gate measured 301 passing with 1 FAILED. The build agent reported 302 passed, 0
failed. My own independent re-measurement earlier tonight also returned 302
passed, 0 failed. Three measurements agreed and all three were wrong.

Re-running P058's suite three times after the gate finished gives **1 failed,
301 passed on 3 of 3 runs**, always the same test:

```
tests/test_properties.py::test_cusum_is_invariant_under_an_affine_rescaling_of_the_channel
```

It is not flaky in the ordinary sense. It is a **Hypothesis property test, and
the gate run is what found the falsifying example.** The agent's runs and my
first run explored a different part of the input space and never reached the
counterexample; once Hypothesis found and cached it, every later run replays it
deterministically. `.hypothesis/` is gitignored, so a fresh clone will pass again
until Hypothesis rediscovers the corner — which is exactly why the falsifying
example is written out in full below rather than left in a cache directory.

**Falsifying example:** `xs=[1.0]`, `h=0.5`, `scale=0.1`.

**Root cause, measured not guessed.** The property under test is that CUSUM,
which standardises by `mu0` and `sigma0`, must reproduce the plain chart exactly
when fed `mu0 + sigma0 * x` — the property that lets a threshold calibrated on
one channel transfer to another. In exact arithmetic it holds. In floating point:

```
y        = 3.0 + 0.1*1.0        = 3.1
z_plain  = 1.0
z_scaled = (3.1 - 3.0)/0.1      = 1.0000000000000009
S+ plain  = max(0, 1.0 - 0.5)                = 0.5
S+ scaled = max(0, 1.0000000000000009 - 0.5) = 0.5000000000000009
```

`detectors.CUSUM` raises an alarm on `max(S_plus, S_minus) > h`, a **strict**
comparison, with `h = 0.5`. So the plain chart gives `False` and the rescaled
chart gives `True`, on a gap of **8.881784197001252e-16** — one ulp of slack at
the exact decision boundary.

**Assessment.** The product's mathematics is correct and the invariance claim is
true in exact arithmetic. What is wrong is the strength of the assertion: a test
that demands bit-exact equality of a *boolean* derived at a threshold boundary is
asserting something floating point cannot deliver, and the docstring's word
"exactly" overstates the guarantee. The honest statement is that threshold
transfer is exact in exact arithmetic and agrees to within rounding, which can
flip a single alarm decision when the statistic lands on `h` to within an ulp.

**This is the same class of defect P057's agent found and fixed in its own
suite tonight** — a one-ulp boundary failure in a no-tolerance property test, at
`n=1249, alpha=0.18`. P057 found its instance because Hypothesis happened to
reach it during the build; P058's instance survived the build and three
measurements and was caught only by the gate. Two independent occurrences in one
batch make this a pattern, not a coincidence: **no-tolerance exact-equality
property tests over floating-point pipelines are a standing defect class in this
mission and should be called out in `PRODUCT_BUILD_GUIDE.md`.**

**Not fixed here.** The standing rule on gate failure is to set the blocked
product to `NEEDS HARDENING`, put the exact gate output in the report, and stop.
A one-line tolerance change is tempting and is still a build action taken after
a gate failure, so it was not taken. The diagnosis above should make the fix a
few minutes' work for whoever picks it up, and the falsifying example should be
pinned as an explicit regression test rather than left to Hypothesis to
rediscover.

**What this vindicates.** "The model that implements a product is never the sole
validator of its own critical numerical claims" earned its keep tonight in the
strongest possible way: the agent's self-report was honest, my independent
re-measurement agreed with it, and both were still wrong. Only the third,
differently-seeded execution found it.

## A second defect found in this session's own work — and it is a mission-wide finding

While the gate ran in the background I committed the final report with `git add -A`.
That swept in **artifact changes the running gate had just made to products it
re-ran**, including a product published three batches ago:

| File | Change |
|---|---|
| `products/P001/screenshots/margin_histogram.png` | 66,047 → 75,602 bytes |
| `products/P051/screenshots/predictor_benchmark.png` | 316,598 → 316,251 bytes |
| `products/P052/validation/validate_benchmark_output.txt` | 6 lines changed |
| `products/P052/validation/validate_difficulty_output.txt` | 4 lines changed |

Caught before pushing. The commit was reset, those three products were restored
to their committed state, and the push contains only this report and the
checkpoint. **No published product was modified.**

Two things follow, and the second is larger than tonight.

1. **Process:** never run `git add -A` while the gate is running. Stage paths
   explicitly. The gate mutates the tree by design, because it re-runs every
   example and every validation script.
2. **The artifact-drift risk is no longer hypothetical, and it reaches
   already-published products.** It has been carried in the checkpoint for three
   sessions as a flagged-but-untested risk. It is now measured. `MISSION_STATUS.md`
   asserts for Batch 05 that `git status` over `products/` after the gate run was
   clean, "so every committed raw validation output, PNG and benchmark record
   still reproduces bit-for-bit from a fresh run." **That property does not hold
   for P001, P051 or P052.** A PNG whose size moves by 9.5 KB is not a timing
   string in a text file; something in that figure is genuinely non-deterministic.

**Measured again at the end of the session, with the full gate run complete, the
drift is larger and has at least three distinct causes.** The finished gate left
**23 tracked files modified** across three products — 9 in P054, 3 in P055, 11 in
P058 — and the diffs are not all timings:

- **Kernel version baked into committed output.** P054's validation scripts
  record `platform.platform()`, so every file carries
  `Linux-6.18.44-fc-v80-…` from the session that generated it and
  `Linux-6.18.44-fc-v114-…` from tonight's. **P054's artifacts will be dirtied by
  every future gate run on a different container**, regardless of timing. This is
  environment provenance, not non-determinism, and it is the easiest of the three
  to fix.
- **Wall-clock timings**, as expected — P055's scale table moves 0.008 → 0.011,
  0.042 → 0.064, 0.173 → 0.299 across the three timed columns while every count
  column is identical, and P058's outputs move similarly.
- **Something in figure generation**, unexplained. P001's
  `margin_histogram.png` moved 66,047 → 75,602 bytes, a 14 % change. That is far
  too large for metadata and was not investigated, because P001 is published and
  this session had no mandate to modify it. **Recorded as unexplained.**

All 23 files were reverted to their committed state and none was pushed.

This does not change any measured test count and does not block anything
tonight. It does mean the bit-for-bit reproducibility claim should be narrowed
to the products where it was actually checked, and that the gate should either
be made artifact-idempotent or be run against a throwaway copy of the tree.
**Flagged as a correction needed to `MISSION_STATUS.md`, not made here** — it is
a claim about five published batches and deserves a session that can measure it
properly rather than a footnote at the end of this one.
