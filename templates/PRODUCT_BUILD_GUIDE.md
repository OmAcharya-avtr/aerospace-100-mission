# Product Build Guide — Batch 1 (binding for all build agents)

You are building one product of a 100-product aerospace software portfolio. Follow every rule below. Deviations must be documented in the product README under Limitations.

## Environment
- Python 3.11, already installed: numpy, scipy, matplotlib, scikit-learn, pytest, hypothesis, ruff, pyyaml, sgp4, pulp, pandas. Do NOT install anything else. PyTorch is NOT available — ML uses scikit-learn or numpy implementations.
- 2 CPU cores. Any training or Monte Carlo run must finish in under 3 minutes. Size datasets/models accordingly and document the compute budget.
- Matplotlib: use the Agg backend (`matplotlib.use("Agg")`), never show().

## Structure (self-contained package, no cross-product imports)
```
products/P0XX/
├── src/<package>/         # code, with docstrings citing equations
├── tests/                  # pytest; must pass with `python -m pytest tests/ -q` run from P0XX/
├── examples/               # runnable scripts; each saves PNG output to ../screenshots/
├── screenshots/            # PNGs produced by actually running examples
├── validation/VALIDATION.md # evidence: what was checked, against what reference, numbers, tolerances
├── validation/*.py          # the scripts that produced the evidence (rerunnable)
├── README.md               # follow templates/PRODUCT_README_TEMPLATE.md structure
├── LICENSE                 # exact license named in the spec; copyright © 2026 OPTIMA Organisation
├── CHANGELOG.md            # 0.1.0 entry
└── pyproject.toml          # name, version 0.1.0, deps, [tool.pytest.ini_options], [tool.ruff]
```

## Engineering honesty (non-negotiable)
- Every physics/engineering equation in code or docs carries: source (author/year or standard), units, assumptions, validity range. Cite real, verifiable references (e.g. Andrews & Phillips 2005 "Laser Beam Propagation through Random Media"; Kim et al. 2001 SPIE 4214; Friis 1946; standard textbook results). NEVER invent a citation, page number, or numerical claim.
- Validation numbers in VALIDATION.md must come from actually running the validation scripts in this session. Save raw script output into validation/ (txt or md). If a check fails, report it as failed — do not tune tolerances to hide it.
- Status vocabulary: use `TESTING` in the README header (QA and batch review happen after your build).
- Required safety statement in every README: this software is research-grade (or educational for L1), not flight-qualified, not certified, not approved for operational aerospace use.
- Required credits line (verbatim, only in Credits section): "This is under reserved rights obtained by OPTIMA Organisation."

## AI products additionally (per mission §11)
- Implement the classical/analytic baseline FIRST; the ML model must be benchmarked against it on the same held-out data.
- Synthetic data is generated by committed scripts (data itself is not committed if > 1 MB; regeneration must be deterministic via fixed seeds).
- MODEL_CARD.md: problem, baseline, architecture, dataset source + limitations, training procedure, metrics, test-split strategy, uncertainty/confidence output, failure cases, reproducibility (exact commands + seeds), compute used, ethical/safety limits, and the statement: "This model is not certified for operational flight use."
- Model must expose an uncertainty or confidence output, not just point estimates.

## Testing minimums
- Compact: unit tests, input validation tests, known-answer tests (hand-calculated, shown in test comments), edge cases.
- Medium: the above + integration test + at least one benchmark/regression test.
- Use Hypothesis for property-based tests where algebraic identities exist.
- Target: every test passes. Do not mark xfail to hide defects; a genuine known limitation may be skipped WITH a documented reason.

## Style
- Ruff-clean (`ruff check src/ tests/` with default rules; line length 100 via [tool.ruff] line-length = 100).
- Type hints on public APIs. Docstrings with units on every public function.
- No `print` in library code; CLI via `python -m <package>` (argparse) where the spec names a CLI.
- Errors: raise ValueError/TypeError with actionable messages on invalid input (negative powers, out-of-range wavelengths, etc.).

## Return format (your final message)
Report: files created (count), test summary (passed/failed/skipped from an actual run), validation highlights (3–5 numbers with references), limitations you documented, and anything that FAILED or was cut. Raw data only — no marketing language.

## Defect classes this mission has actually shipped (binding, added 2026-10-11)
Each item below is a defect that reached a published or gate-blocked product. They
are listed because a build agent reading a generic instruction did not avoid them.

### Re-run every README-quoted command as the LAST step before you hand back
Recommended by three consecutive sessions (2026-10-08, 2026-10-09, 2026-10-10) and
now binding. Every command, number and output fragment quoted in README.md,
VALIDATION.md or MODEL_CARD.md is re-executed after the final code change, and the
quoted text is replaced with what the run actually printed. This is not ceremony:
P052 and P056 each caught their OWN wrong README numbers this way, in consecutive
batches. P056 found four, including three decomposition residuals that moved when it
vectorised a binning accumulator and a hand-rendered 0.500000000000000 for a value
that is in fact 0.49999999999999983.

### Never assert bit-exact equality over a floating-point pipeline
Two independent occurrences in Batch 06 alone, so this is a class and not an
incident.

- P057 asserted an exact coverage identity and failed at n=1249, alpha=0.18 because
  1-0.18 evaluates to 0.8200000000000001.
- P058 asserted that a CUSUM alarm boolean is invariant under an affine rescaling of
  the channel. The mathematics is correct in exact arithmetic. It survived the build,
  the agent self-report AND the coordinator re-measurement, and was falsified only by
  the release gate at xs=[1.0], h=0.5, scale=0.1, where the statistic lands on the
  decision interval to within one ulp and the strict comparison flips.

Rules:

1. Compare floating-point statistics with a tolerance on both sides.
2. NEVER assert equality of a BOOLEAN produced by a strict threshold comparison. The
   boolean is a step function of a rounded quantity; it is the one thing floating
   point cannot promise. Assert the statistics agree to tolerance, and allow the
   boolean to differ only when the statistic sits within tolerance of the threshold.
3. Say in the docstring what is actually guaranteed. The word exactly is a claim.
   Exact in exact arithmetic, agreeing to within rounding, is the honest phrasing.
4. .hypothesis/ is gitignored, so a falsifying example found by one run is LOST on a
   fresh clone. Pin every counterexample Hypothesis finds as an explicit, named
   regression test with the literal inputs in the test body.

### Anchor scratch-file patterns in .gitignore
A gitignore pattern with no slash matches at ANY depth. A bare junit.xml in a product
.gitignore silently excluded products/P060/fixtures/sample_project/junit.xml, a
REQUIRED committed deliverable. P060 passed every local check because the agent
tested an uncommitted working tree where the file was present on disk, and a cold
clone then failed with 17 failures and 9 errors. Write /junit.xml, not junit.xml.
Before handing back, run git check-ignore -v against every fixture and data file your
product is supposed to ship.

### Count tests from junit XML, never from pytest stdout
A suite that collects zero tests prints success and exits 0. That is how P001 shipped
publicly with a recorded 251 tests passing and a config that collected none, for three
weeks. Parse the testsuite element and cross-check it against a count of testcase
elements.

### Validation output layout — one convention
Flat: validation/<script-name>_output.txt, beside the script. This is P059 layout and
is what P057, P059 and P060 use. Binding for Batch 07 onward. Batch 06 contains both
this and validation/outputs/ (P056, P058); normalising those two is a git mv plus a
path edit in the script and the README, and it must be done by a session that can
re-run the scripts and the gate afterwards, because the quoted paths are part of the
checked output.

### A dependency floor with no ceiling is not a dependency specification (added 2026-10-14)
On 2026-10-13 `scripts/cold_clone_check.py` was executed for the first time over
all sixty products and found **five of the fifty published products broken or
silently wrong for a new install**. Every one of the five was a declared
dependency range that had a floor and no ceiling, so pip resolved a major
version released after the product was measured.

- **P001** `scikit-learn>=1.3`: 4 of 251 tests errored because scikit-learn 1.9
  cannot unpickle a model written by 1.8.0.
- **P004** `pulp>=2.7`: 17 of 106 failed; PuLP 4.0 removed `LpVariable(cat=)`.
- **P023** `pulp>=2.7`: 1 of 185 failed; PuLP 4.0 removed `PULP_CBC_CMD`, and
  PuLP 2.9 has no `add_variable`, so it needs 3.x **specifically**.
- **P032** `pulp>=2.7`: 25 of 387 failed on PuLP **2.9.0** — broken at the
  **floor**, not the ceiling, because it was written against 4.0.0.
- **P025** `scikit-learn>=1.3`: the suite passes on both versions and the
  *validation numbers change* — 0.1500 → 0.1444 false alarms, 220/306000 →
  208/306000. The silent one is the dangerous one.

Rules:

1. **Bound every dependency on both sides.** Declare the range you actually
   measured: `>=1.8,<1.9`, not `>=1.3`.
2. **Never bound a dependency from a README, a changelog or reasoning about
   what an API probably still looks like.** Commit `9eea674` bounded P004 to
   `<3` by reading its README; execution then showed its published numbers came
   from 3.x, that P023 works on 3.x only, and that P032 — which the same
   reasoning would also have bounded to `<3` — *loses 25 tests* on 2.9.0. Two
   of three bounds derived by reasoning were wrong. Install each end of the
   range and run the suite.
3. **A product that commits a pickled or otherwise serialised artifact must
   bound the library that wrote it**, to the minor version, because the
   serialisation format is not part of that library's public API contract.
4. **Run the suite at both ends of every declared range before handing back,
   and diff the committed validation output, not just the test verdict.** A
   suite that passes while its validation numbers move is the P025 class and no
   test will catch it.
5. A pin below a future security release is a real cost, not a free safety
   measure: the product cannot take that release without a port. Record the
   tension in Limitations; do not resolve it by removing the ceiling.

### A validation script must run from ANY working directory (added 2026-10-17)

Three products in one batch — P065, P066, P069 — failed the release gate on
2026-10-16 after passing every check that preceded it, because
`validation/worked_example.py` passed a bare relative path
(`examples/cases/*.yaml`, `fixtures/space.json`) to a loader. Measured on P066:
exit 0 from `products/P066/`, exit 1 from anywhere else.

Nothing in the build caught it, and the reason is worth stating: the build
agent, the agent's own self-report and the coordinator's re-measurement all ran
the script the same way — from the product root. The gate runs it with
`cwd=validation/`. Three independent verifications agreeing does not help when
they share an assumption.

The rule:

- Anchor on `__file__`, never on the caller's working directory. In the
  validation support module, after putting `src` on `sys.path`:
  `ROOT = Path(__file__).resolve().parent.parent` then `os.chdir(ROOT)`.
  One line fixes every script in the directory, and it is a no-op when the
  script is already run from the product root.
- Verify it. Run each script from at least `/`, `/tmp`, the product root and
  `validation/` and require exit 0 from all four. Do not infer this from a
  single run.

### Committed validation output must not carry an absolute path (added 2026-10-17)

Release-gate check 8 fails the whole batch on an absolute home-directory path in
any tracked file. Five Batch 07 products tripped it from output files, not from
code: a script printed `{ROOT}`, or passed an absolute path to a loader whose
error message then quoted it back.

- Print paths relative to the repository root (`ROOT.relative_to(ROOT.parent.parent)`).
- Name probe paths relatively, so a product's own error text quotes a relative
  path. This is why the `os.chdir(ROOT)` above matters twice.
- When a captured transcript cannot avoid an absolute path, normalise it out
  before writing, and say in the script's own comments that you did.

An absolute path in committed output is not cosmetic: it is not reproducible for
a reader cold-cloning the repository, and it publishes the build machine's
filesystem layout.
